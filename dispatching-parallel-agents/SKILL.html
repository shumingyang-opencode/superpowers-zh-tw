Dispatching Parallel Agents

派發並行代理

Overview

總覽

You delegate tasks to specialized agents with isolated context. By precisely crafting their instructions and context, you ensure they stay focused and succeed at their task. They should never inherit your session's context or history — you construct exactly what they need. This also preserves your own context for coordination work.

你將任務委派給具備隔離上下文的專門代理。透過精確構思它們的指令與上下文，你確保它們能保持專注並成功完成任務。它們不應繼承你 session 的上下文或歷史 —— 你為它們建構所需的全部內容。這也為協調工作保留了你的上下文。

When you have multiple unrelated failures (different test files, different subsystems, different bugs), investigating them sequentially wastes time. Each investigation is independent and can happen in parallel.

當你有多個互不相關的失敗（不同的測試檔、不同的子系統、不同的 bug）時，逐一調查會浪費時間。每次調查都彼此獨立，可以並行進行。

Core principle: Dispatch one agent per independent problem domain. Let them work concurrently.

核心原則： 每個獨立的問題領域派發一個代理，讓它們並行運作。

Use when: - 3+ test files failing with different root causes - Multiple subsystems broken independently - Each problem can be understood without context from others - No shared state between investigations

使用時機： - 3 個以上測試檔因不同根因而失敗 - 多個子系統各自獨立損壞 - 每個問題無需依賴其他問題的上下文即可理解 - 各調查之間沒有共享狀態

Don't use when: - Failures are related (fix one might fix others) - Need to understand full system state - Agents would interfere with each other

不要使用的時機： - 失敗彼此相關（修好一個可能連帶修好其他） - 需要理解完整的系統狀態 - 代理會互相干擾

The Pattern

模式

1. Identify Independent Domains

1. 識別獨立的問題領域

Group failures by what's broken: - File A tests: Tool approval flow - File B tests: Batch completion behavior - File C tests: Abort functionality

按損壞的內容對失敗分組： - 檔案 A 測試：工具核准流程 - 檔案 B 測試：批次完成行為 - 檔案 C 測試：中止功能

Each domain is independent - fixing tool approval doesn't affect abort tests.

每個領域彼此獨立 —— 修正工具核准不會影響中止測試。

2. Create Focused Agent Tasks

2. 建立聚焦的代理任務

Each agent gets: - Specific scope: One test file or subsystem - Clear goal: Make these tests pass - Constraints: Don't change other code - Expected output: Summary of what you found and fixed

每個代理會收到： - 明確範圍： 單一測試檔或子系統 - 清楚目標： 讓這些測試通過 - 限制： 不要更動其他程式碼 - 預期輸出： 你發現與修正內容的摘要

3. Dispatch in Parallel

3. 並行派發

Issue all three subagent dispatches in the same response — they run in parallel:

在同一則回應中發出全部三個子代理派發 —— 它們會並行執行：

Subagent (general-purpose): "Fix agent-tool-abort.test.ts failures"
Subagent (general-purpose): "Fix batch-completion-behavior.test.ts failures"
Subagent (general-purpose): "Fix tool-approval-race-conditions.test.ts failures"
# All three run concurrently.

Subagent (general-purpose): "Fix agent-tool-abort.test.ts failures"
Subagent (general-purpose): "Fix batch-completion-behavior.test.ts failures"
Subagent (general-purpose): "Fix tool-approval-race-conditions.test.ts failures"
# All three run concurrently.

Multiple dispatch calls in one response = parallel execution. One per response = sequential.

一則回應中多次派發呼叫 = 並行執行。每則回應一次 = 循序執行。

4. Review and Integrate

4. 審查與整合

When agents return: - Read each summary - Verify fixes don't conflict - Run full test suite - Integrate all changes

當代理回報時： - 閱讀每份摘要 - 確認修正彼此不衝突 - 執行完整的測試套件 - 整合所有變更

Agent Prompt Structure

代理 Prompt 結構

Good agent prompts are: 1. Focused - One clear problem domain 2. Self-contained - All context needed to understand the problem 3. Specific about output - What should the agent return?

良好的代理 prompt 具備： 1. 聚焦 - 單一清晰的問題領域 2. 自足 - 包含理解問題所需的全部上下文 3. 明確輸出 - 代理應該回傳什麼？

Common Mistakes

常見錯誤

❌ Too broad: "Fix all the tests" - agent gets lost ✅ Specific: "Fix agent-tool-abort.test.ts" - focused scope

❌ 範圍過大： 「修好所有測試」- 代理會迷失方向 ✅ 具體明確： 「修好 agent-tool-abort.test.ts」- 範圍聚焦

❌ No context: "Fix the race condition" - agent doesn't know where ✅ Context: Paste the error messages and test names

❌ 沒有上下文： 「修正競爭條件」- 代理不知道在哪裡 ✅ 提供上下文： 貼上錯誤訊息與測試名稱

❌ No constraints: Agent might refactor everything ✅ Constraints: "Do NOT change production code" or "Fix tests only"

❌ 沒有限制： 代理可能重構一切 ✅ 設定限制： 「不要更動正式程式碼」或「只修正測試」

❌ Vague output: "Fix it" - you don't know what changed ✅ Specific: "Return summary of root cause and changes"

❌ 輸出含糊： 「修好它」- 你不知道改了什麼 ✅ 具體明確： 「回傳根因與變更的摘要」

When NOT to Use

何時不該使用

Related failures: Fixing one might fix others - investigate together first Need full context: Understanding requires seeing entire system Exploratory debugging: You don't know what's broken yet Shared state: Agents would interfere (editing same files, using same resources)

相關失敗： 修好一個可能連帶修好其他 —— 先一起調查 需要完整上下文： 必須檢視整個系統才能理解 探索式除錯： 你尚不知道哪裡壞了 共享狀態： 代理會互相干擾（編輯相同檔案、使用相同資源）

Real Example from Session

實際會話範例

Scenario: 6 test failures across 3 files after major refactoring

情境： 大型重構後 3 個檔案共 6 個測試失敗

Failures: - agent-tool-abort.test.ts: 3 failures (timing issues) - batch-completion-behavior.test.ts: 2 failures (tools not executing) - tool-approval-race-conditions.test.ts: 1 failure (execution count = 0)

失敗： - agent-tool-abort.test.ts：3 個失敗（時序問題） - batch-completion-behavior.test.ts：2 個失敗（工具未執行） - tool-approval-race-conditions.test.ts：1 個失敗（執行次數 = 0）

Decision: Independent domains - abort logic separate from batch completion separate from race conditions

決策： 獨立領域 —— 中止邏輯、批次完成、競爭條件各自獨立

Dispatch:

Agent 1 → Fix agent-tool-abort.test.ts
Agent 2 → Fix batch-completion-behavior.test.ts
Agent 3 → Fix tool-approval-race-conditions.test.ts

派發：

Agent 1 → Fix agent-tool-abort.test.ts
Agent 2 → Fix batch-completion-behavior.test.ts
Agent 3 → Fix tool-approval-race-conditions.test.ts

Results: - Agent 1: Replaced timeouts with event-based waiting - Agent 2: Fixed event structure bug (threadId in wrong place) - Agent 3: Added wait for async tool execution to complete

結果： - Agent 1：以事件驅動等待取代 timeout - Agent 2：修正事件結構 bug（threadId 放錯位置） - Agent 3：新增等待非同步工具執行完成

Integration: All fixes independent, no conflicts, full suite green

整合： 所有修正彼此獨立、無衝突，完整測試套件全綠

Verification

驗證

After agents return: 1. Review each summary - Understand what changed 2. Check for conflicts - Did agents edit same code? 3. Run full suite - Verify all fixes work together 4. Spot check - Agents can make systematic errors

代理回報後： 1. 審查每份摘要 - 了解變更了什麼 2. 檢查衝突 - 代理是否編輯了相同的程式碼？ 3. 執行完整套件 - 確認所有修正能共同運作 4. 抽樣檢查 - 代理可能犯系統性錯誤

教學解說

並行派發子代理的關鍵是任務之間必須互相獨立。如果 Task B 依賴 Task A 的結果，它們就不能並行——必須排成序列。

並行的優勢是速度：三個獨立的 API 端點可以同時實作。但並行的代價是整合風險：三個子代理可能做出互相衝突的決策。

Worked Example（具體案例）

案例：建立三個獨立的 API 端點

  1. 確認：/api/users、/api/posts、/api/comments 互相獨立
  2. 同時派發三個子代理，每個負責一個端點
  3. 三個都完成後，做整合測試確認沒有衝突

常見錯誤

錯誤正確做法
把有依賴的任務並行派發確認獨立性後才並行
不檢查衝突就合併結果並行完成後做整合測試

練習／檢核清單

  • □ 已確認任務之間互相獨立
  • □ 已同時派發所有獨立任務
  • □ 並行完成後已做整合測試

進階真實情境 Worked Example

案例：大型重構後，CI 在三個完全不同模組各掛了數個測試

  1. 分組判斷獨立性——失敗分佈在 auth（OAuth 換發 token）、search（索引查詢）、notifications（推播排程）三個模組，diff 顯示重構動的檔案互不重疊
  2. 確認「修 A 不會修到 B」——比對三個模組的共用函式清單，確認各自只依賴穩定基礎層，才判定為獨立領域
  3. 同一則回應中並行派發三個子代理——每個 prompt 都自足：包含該模組的失敗測試名稱、錯誤訊息、以及「不要更動其他模組」的硬性限制
  4. 各自回報摘要——auth：發現 refresh token 的 exp 欄位解析型別錯誤；search：索引版本號沒遞增；notifications：時區換算少了 UTC 偏移
  5. 整合驗證——三個 fix 不相衝突，合併後跑完整 CI，全綠

為什麼選這條路徑：三個失敗的根因彼此無關，逐一調查要串三個回合、且每一回合都重載同一個大 context。並行派發把三個獨立的調查同時丟出去，主代理的上下文只留下三份摘要，而不是三份調查過程。

深入原理擴充

「一則回應中多次派發 = 並行；每則回應一次 = 循序」——這背後是 agent harness 對工具呼叫的執行模型：同一則 assistant message 裡的多個 tool call 會被排入平行佇列，各自擁有獨立的子代理上下文與 token 預算。這正是 superpowers 刻意利用的機制：子代理「不繼承你的 session 歷史」不是缺點，而是並行安全的前提——三個子代理各自讀同一份 repo 但不共享可變狀態。

陷阱藏在「獨立性」的判斷上：「測試檔不同」不代表「根因獨立」。兩支測試可能都失敗在同一個 shared helper 的型別錯誤上——這類失敗修好一個就會連帶修好另一個，並行派發反而讓三個子代理同時改同一份 helper，製造 merge conflict。技能流程圖裡的「Are they independent?」這顆菱形，就是要求你在派發前先查共用依賴。

陷阱案例：只憑目錄名判斷獨立。把 tests/auth.test.ts 與 tests/auth-integration.test.ts 當成兩個獨立領域派發，結果兩支測試其實都在打同一支 refreshToken()，而它是唯一的 bug 來源。兩個子代理各自「修好」自己那支測試，實作互相矛盾，整合時才爆發。判斷獨立性的正確動作是：先看兩個領域的共同依賴集合是否為空。

症狀可能原因解決方案

子代理回報「我發現它其實是另個模組的 bug」獨立性判斷失準，領域界線與程式碼不符停下收集回報，重新分組後再派一輪，不要硬拼

進階挑戰題

  1. 兩個測試檔分別失敗，但它們都 import 同一支 formatDate()。你如何用一行指令判斷它們是否屬於獨立領域？
  2. 並行派發的三個子代理各回報了「修復完成」，但整合時 CI 仍掛。除了子代理謊報，還有什麼系統性原因？你要如何防禦？
  3. 某個子代理的 prompt 寫了「不要更動其他模組」，它卻改了。這代表 prompt 結構的哪個環節失效？應該在 prompt 裡加什麼來補強？

Superpowers 方法論總覽

它跟一般的「技能包」差在哪？為什麼整套會「自己跑起來」？

一、它不是 14 個孤立的技能，而是一套流程

很多技能包只是「一袋工具」——需要時才拿出來用，平時擺著。Superpowers 不是。它的核心主張是：這 14 個技能接成一條完整的開發工作流，從「你冒出一個想法」一路到「程式碼合併上線」。

而且關鍵在於：流程是自動觸發的。開場指令（using-superpowers）讓 agent 在「任何回應之前」先檢查有沒有技能適用——這不是建議，是強制。所以你不必記得去呼叫技能，agent 會在你動手之前先把你推到正確的流程上。

二、流程的七個階段

階段技能做什麼
0. 開場using-superpowers每個 session 啟動時注入：先檢查技能，再行動
1. 腦力激盪brainstorming動工前把點子敲成設計——agent 反問你，直到設計明確
2. 開 worktreeusing-git-worktrees建立隔離工作區，主分支不受干擾
3. 寫計畫writing-plans把設計拆成 2–5 分鐘的小任務，每個都標檔案與驗證方式
4. 執行subagent-driven-development / executing-plans逐任務派子代理實作，兩階段審查（規格 → 品質）
5. 測試test-driven-development實作過程強制 RED-GREEN-REFACTOR
6. 審查requesting / receiving-code-review任務之間與收尾前送審，按嚴重度回報
7. 收尾finishing-a-development-branch全綠之後，決定合併／發 PR／保留／丟棄

另有兩個「遇到問題隨時進來」的支線：systematic-debugging（出 bug 時）與 verification-before-completion（宣告完成前），以及一個 meta 技能 writing-skills（怎麼寫新技能）。

三、三個設計選擇，讓它跟別人不一樣

1. 技能自己會觸發auto-triggering

不用你記指令。開場指令強制 agent 在回應前檢查技能適用性。這解決了「技能裝了但永遠沒被用」的通病。

2. 子代理驅動subagent-driven development

每個任務派「全新的子代理」實作，一次只做一件事，做完立刻兩階段審查。子代理沒有你對話的上下文，反而迫使它照計畫行事、產出可驗證的結果。

3. 證據優先evidence over claims

「測過了」「應該可以」都不算數。TDD 要求親眼看測試紅、再親眼看它綠；verification-before-completion 要求真的跑指令、貼出輸出。用證據取代宣稱。

四、為什麼「先寫失敗的測試」這麼重要

Superpowers 把 TDD 當成鐵律：沒有先寫失敗的測試，就不准有正式程式碼。原因很務實——你沒看過測試失敗，你就不知道它測的是不是對的東西。事後補的測試永遠會通過，卻證明不了任何事。這條鐵律貫穿整個流程，寫技能、修 bug、做功能都一樣。

五、跟其他方法論的差別

GSD、BMAD、Spec-Kit 這類做法「接管流程」——它們拿走你的控制權，讓流程本身的 bug 難以解決。Superpowers 反過來：技能小、容易改、可組合，agent 只是照著技能指示行動，你隨時保有控制權。這跟 mattpocock/skills 的設計哲學一致：給真人工程師掌控，而不是讓流程凌駕於你之上。

六、從哪裡開始

  1. 裝好之後，直接說「我們來做 X」——它會自動帶你走完流程。
  2. 想先看懂全貌：看 全景圖。
  3. 想照順序學：走 學習路線。
  4. 想深入某個環節：工作流拆解 或 SDD 深入。

教學解說

這篇方法論總覽的核心訊息是：Superpowers 不是一袋零散的工具，而是一條完整的開發管線。理解這一點是使用 Superpowers 的第一步。

很多人會犯的錯誤是「只用其中幾個技能」——例如只用 brainstorming 和 TDD，但跳過 writing-plans 和 code review。這就像只用一半的流水線：前面做得再好，後面也會出問題。

另一個常見誤解是「技能需要手動觸發」。事實上 using-superpowers 會強制在任何回應前檢查技能適用性。這意味著你不需要記住「什麼時候該用什麼技能」——系統會自動把你推到正確的流程上。

Worked Example（具體案例）

案例：新手第一次使用 Superpowers

  1. 安裝 Superpowers 後，直接說「幫我建一個 Todo List 功能」
  2. 系統自動進入 brainstorming → 反問：要支援哪些功能？需要帳號系統嗎？
  3. 設計完成後自動建立 worktree → 自動撰寫計畫
  4. 執行計畫時自動派子代理、自動跑 TDD
  5. 完成後自動送 code review → 自動呈現合併選項

整個過程你只需要說一句話，系統就會自動走完所有階段。

常見錯誤

錯誤正確做法
只用部分技能讓系統自動觸發所有必要技能
手動觸發技能信任 using-superpowers 的自動觸發
跳過 brainstorming 直接實作即使是「很簡單」的功能也要走 brainstorming

練習／檢核清單

  • □ 已理解 Superpowers 是一條完整管線，不是零散工具
  • □ 已安裝並確認 using-superpowers 正常運作
  • □ 已嘗試說一句話讓系統自動走完流程
  • □ 已理解七個階段各自的角色

進階真實情境 Worked Example

案例：從「GSD 式接管流程」遷移到 Superpowers 的團隊，第一個完整週期

  1. 遷移前的差異盤點——舊流程「定義→分解→執行」由平台強制，代理被關在固定模板裡；Superpowers 是技能層的指示，代理照做但你隨時能改
  2. 第一個功能——「加一個匯出儀表板的 CSV 功能」：using-superpowers 自動觸發 brainstorming，資深者第一次體驗「代理反問需求、而不是直接做」；設計核准後自動開 worktree、寫計畫
  3. 執行途中出問題——任務 3 的計畫假設過時，子代理回報 BLOCKED。團隊沒有「硬闖」，而是停下改計畫再續跑——這正是「你保有控制權」的證明
  4. 收尾——全綠後呈現四選項，團隊選擇先發 PR 讓其他部門 review；worktree 保留等回饋
  5. 回顧——週五回顧：把「中途改計畫」的經驗寫回 team wiki，並決定調整 brainstorming 對「匯出類功能」的預設問題清單

為什麼選這條路徑：遷移最大的文化差異是「誰有最終決定權」。GSD 類做法讓流程凌駕於人；Superpowers 讓技能服務於人。這個案例刻意展示「計畫可以改、決策可以覆蓋、技能可以客製」——理解這三點，才不會把 Superpowers 用成另一個 GSD。

深入原理擴充

「自動觸發」是這套方法論與「技能包」的分水嶺，而它的機制值得拆解：using-superpowers 不是一個「檢查一次」的開場白，而是一個持續生效的上下文常數。它被注入每個 session 的開頭，持續佔據模型注意力，讓「先檢查技能再行動」成為每次生成前的隱含約束。自動觸發的價值不在「提醒」，而在於把流程決策從記憶負擔變成系統行為——人不靠記得，agent 不靠提醒。

「14 個技能接成一條管線」的另一面是狀態的流動：brainstorming 的輸出（設計文件）是 writing-plans 的輸入，writing-plans 的輸出（計畫）是執行的輸入。每一站產出的「文件」都是下一站的上下文，管線才會「自己跑起來」。這也解釋了為什麼文件位置被寫死（docs/superpowers/specs/、plans/）——交接文件必須有穩定的地址，管線才找得到。

陷阱案例：只移植「看起來好用」的幾個技能。「我們用 brainstorming 和 TDD 就好，跳過計畫和審查」——這是最常見的遷移半吊子。它的問題不是「少了幾個環節」，而是斷了管線：沒有 writing-plans，執行時沒有契約；沒有 code review，錯誤拖到合併前才發現；沒有 worktree，主分支隨時被污染。流程不是菜單，你無法只點前菜與甜點。

診斷式疑難排解表

症狀可能原因解決方案
技能裝了但從沒自動觸發using-superpowers 沒安裝或版本不符確認開場指令注入正常；用「我們來做 X」實測觸發
代理繞過 brainstorming 直接做觸發被使用者指示或上下文壓過檢查是否有 AGENTS.md／CLAUDE.md 覆蓋；無則要求代理補走流程
文件路徑找不到（specs/plans 消失）專案沒有預設目錄或偏好設定遺失建立 docs/superpowers/ 目錄結構，確認技能可寫入
管線跑到一半「斷電」session 中斷，狀態沒落盤靠已 commit 的設計／計畫文件續跑；重跑 executing-plans
團隊質疑「太多流程、太慢」把流程成本與不確定性成本混為一談用證據比較：有流程的返工次數 vs 無流程的返工次數

進階挑戰題

  1. 「自動觸發」為什麼必須是「任何回應之前」，而不是「開始工作之前」？若改成後者，會漏掉哪一種情況？
  2. 如果一個團隊只用 brainstorming＋TDD，管線在哪兩個點斷掉？斷點各自造成什麼後果？
  3. 「文件位置寫死」對管線的意義是什麼？若每個人自訂規格檔位置，管線會發生什麼事？

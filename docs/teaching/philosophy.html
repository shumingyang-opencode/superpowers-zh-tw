哲學四原則

Superpowers 的信仰宣言——四個原則如何滲透到每個技能

原則一：測試驅動開發（永遠先寫測試）

口號：「沒有先寫失敗的測試，就不准有正式程式碼。」

這不是口號，是鐵律。從 test-driven-development 到 writing-skills（寫技能也要先有會失敗的測試）再到 systematic-debugging（修 bug 前先寫一支會紅的測試），整個流程每一環都被同一條紀律把關。

為什麼？因為回饋的速度就是你的速度上限。你沒看過測試失敗，就不知道它在測什麼；你沒看過它變綠，就不知道程式真的做了你以為的事。TDD 讓代理每次都拿到「程式真的在運作」的證據，而不是「我猜應該可以」。

原則二：系統化勝於 ad-hoc（流程勝於瞎猜）

Superpowers 的每個技能都是一套明確的流程，不是一段建議。brainstorming 有它的提問結構，systematic-debugging 有它的四階段，subagent-driven-development 有它的任務迴圈與兩階段審查。

ad-hoc 依賴運氣：這把 bug 看起來像那回事就試試看，這次憑感覺改一改。系統化則保證每次都走同一條被驗證過的路。代理壓力越大，越需要流程——壓力會讓人（跟代理）退回憑感覺。

原則三：降低複雜度（簡潔是首要目標）

設計文件、計畫、測試、技能文件——全都要求最小、夠用就好。writing-plans 把任務拆到 2–5 分鐘，writing-skills 要求技能文件 <500 字、常用技能 <200 字。複雜度是累積的：每個多餘的環節都會在未來的每個 session 消耗 token 與注意力。

「YAGNI（You Aren't Gonna Need It）」與「DRY」不只是 coding 原則，也被套用到流程本身：不加不需要的環節，不重複寫已經有技能涵蓋的指示。

原則四：證據勝於宣稱（驗證成功才叫成功）

「測過了」「應該可以」「我記得它可以用」——全部不算數。verification-before-completion 要求：宣告完成之前，真的跑驗證指令、貼出輸出、確認結果。TDD 要求親眼看到紅與綠。

這條原則直接對抗代理最大的通病：過度自信地宣告成功。它把「證據」設為唯一可接受的完成標準，斷言之前必須先有輸出。

四原則如何互咬

這四條不是獨立的口號，它們互相支撐：

  • TDD 提供證據（原則一 → 原則四）。
  • 系統化流程讓 TDD 不會被繞過（原則二 → 原則一）。
  • 簡潔讓流程可持續、不嚇人（原則三 → 原則二）。
  • 證據原則反過來驗證流程本身有效（原則四 → 原則二）。

想看到它們在實際工作中怎麼落地，看 基本工作流拆解 或直接進 全景圖。

教學解說

Superpowers 的四個哲學原則不是裝飾——它們是所有技能的設計基礎。當你理解這些原則後，你就能理解為什麼每個技能要這樣設計。

例如：TDD 原則解釋了為什麼所有測試都必須先看到失敗；系統化原則解釋了為什麼除錯有四個嚴格的階段；降低複雜度原則解釋了為什麼任務要拆成 2-5 分鐘的小塊；證據優先原則解釋了為什麼不能只說「應該可以」。

Worked Example（具體案例）

案例：四個原則如何影響實務決策

  • TDD：寫了一個函式 → 不是先寫實作再補測試，而是先寫會失敗的測試
  • 系統化：遇到 bug → 不是「試試看」，而是走四階段根因流程
  • 降低複雜度：計畫太大 → 不是「硬著頭皮做」，而是拆成子計畫
  • 證據優先：宣稱完成 → 不是說「應該沒問題」，而是跑測試貼輸出

常見錯誤

錯誤正確做法
把原則當建議原則是強制要求，不是「看情況」
覺得「這次例外」每次例外都是技術債的來源

練習／檢核清單

  • □ 已理解四個哲學原則
  • □ 已理解每個原則如何影響技能設計
  • □ 已理解「違反字面就是違反精神」的含義

進階真實情境 Worked Example

案例：生產事故後，四個原則如何同時介入同一次修復

  1. 事故——凌晨警報：付款結算延遲 20 分鐘。值班者第一個念頭：「先手動跑一次結算補上。」
  2. 原則二（系統化）攔截——「手動跑一次」是 ad-hoc 症狀修復；先走 systematic-debugging 四階段，調查「為什麼排程沒觸發」
  3. 原則一（TDD）支援——調查發現排程邏輯的時區判斷少了一小時。先寫一支會紅的測試重現「跨日邊界不排程」，再寫最小修復
  4. 原則四（證據）把關——值班者不只要「覺得修好了」：重跑排程測試、模擬一次完整結算，貼出輸出才宣告解除
  5. 原則三（降低複雜度）收尾——檢視時區邏輯，發現兩處重複的時間轉換，抽出單一 helper（DRY），並移除手動補跑用的後門——它正是這次事故能「靠手動補」的誘因
  6. 回顧——寫一篇 postmortem，用四原則的語言描述每個決策點「為什麼這樣做」

為什麼選這條路徑：四個原則不是四支獨立的技能，而是同一件事的四個剖面。事故現場最需要的是「先系統化別瞎修」，而它會自然帶出「用測試證實、用證據宣告、用簡潔收尾」——順序本身就是原則互相支撐的實例。

深入原理擴充

四原則的「互咬」結構（TDD 供證據 → 系統化讓 TDD 不被繞過 → 簡潔讓系統化可持續 → 證據驗證系統化有效）值得拆解成一個強化迴圈：每條原則要麼為下一條提供輸入，要麼被下一條保護。這不是修辭上的排列，而是設計上的依賴——抽掉任何一條，其他三條都會失去支撐。例如沒有「證據」原則，TDD 的「親眼看到紅」就退化成「我有測試」；沒有「系統化」原則，TDD 在壓力下會被繞過。

「違反字面＝違反精神」這句格言的機制是：字面是紀律的最小可執行單元，精神是紀律的完整意圖。規則設計者知道模型（與人）會找字面漏洞——「測試我寫了，只是先跑了」——所以把「精神」也寫進條文，讓違反者無法用「我沒違反字面」自我開脫。這是把「防繞路」直接寫進文件語言的技巧。

陷阱案例：把原則當「看情況」的建議。「這次是緊急事故，先跳過流程」是最常見的原則背叛。系統化原則明說「緊急時更需要流程」——壓力會讓決策退回憑感覺，而系統化正是對抗憑感覺的結構。每次「例外」都是技術債的種子：這次跳過測試，下次就沒有測試證明這次修對了；這次跳過驗證，下次就靠運氣確認。原則的價值恰恰在壓力最大的時候，而不是順風時。

診斷式疑難排解表

症狀可能原因解決方案
「我覺得該走流程，但時間不允許」把流程想成慢路、把瞎修想成快路比較返工成本：系統化平均比亂試快（技能原文明言）
「測試都過，但需求沒達成」測試存在 ≠ 測試有承載（空斷言／測錯目標）回歸「證據」原則：刪實作看測試是否紅，紅才有效
「這個任務太簡單，不用寫計畫」複雜度原則被誤用為「省略」簡潔是「夠用就好」，不是「沒有也行」；簡單計畫只要幾句話
四原則各自為政、互相打架沒理解強化迴圈結構用「互咬」圖檢視：抽掉一條，其他三條如何失支撐
「上次我們就是這樣，所以這次也行」把「前例」當成「原則」前例是證據來源，原則才是決策依據；驗證前例是否違反原則

進階挑戰題

  1. 用四原則的語言，分析「我先把修復寫好，再補測試」這個行為——它違反哪一條？連帶會讓哪一條失效？
  2. 「降低複雜度」若被誤解成「流程越少越好」，會造成什麼？它真正的意思是什麼？
  3. 舉一個「字面遵守、精神違反」的例子（四原則任一條），並說明你如何判斷它違反了精神。

專案級端到端 Worked Example

案例：四原則在「開源專案貢獻」中的實踐——從 TDD 到證據勝於宣稱的完整應用

  1. 原則一：TDD——為開源專案的 PR 寫回歸測試：先寫「現有行為會失敗」的測試（RED），再提 PR（GREEN 的一半）， maintainer 合併後確認測試通過（GREEN 的另一半）
  2. 原則二：系統化——用 PR template 確保每個 PR 都經過：需求描述、測試證明、文件更新、安全掃描——不靠記憶，靠流程
  3. 原則三：簡潔——PR description 只寫「做了什麼、為什麼、怎麼測」，不寫故事、不寫心路歷程——YAGNI 也適用於溝通
  4. 原則四：證據——PR 中附上 CI 綠燈截圖、測試覆蓋率報告、效能基準比較——「我測過了」不算數，截圖才算數

為什麼選這條路徑：開源貢獻是「四原則如何在沒有職權的環境中運作」的最佳案例：你不能強制 maintainer 走流程，但你可以用流程的產出（測試、截文件、CI 證據）說服他們。四原則在這裡的角色是「品質的通用語言」——即使 maintainer 不知道 Superpowers，他們也能從「有測試、有證據、有文件」的 PR 中判斷品質。

效能／品質／安全深度

效能：四原則的成本效益：TDD 在開源貢獻中的 ROI 最高——回歸測試不只證明你的 PR 正確，還保護未來的 contributor 不會不小心 break 你修復的功能。系統化的 PR template 增加 5 分鐘的填寫時間，但減少 80% 的 maintainer 追問（「你怎麼測的？」「為什麼改這個？」「有沒有安全風險？」）。

品質：四原則的品質互咬結構：TDD 提供證據（原則一→原則四），系統化確保 TDD 不被繞過（原則二→原則一），簡潔讓系統化可持續（原則三→原則二），證據反過來驗證系統化有效（原則四→原則二）。在開源貢獻中，這個互咬結構的價值是「可預測性」——maintainer 知道你的每個 PR 都經過同樣的品質把關，不用逐個判斷。

安全：開源貢獻的安全特殊性：1. 你的 PR 可能被數千人使用——安全影響範圍比內部專案大得多；2. TDD 的回歸測試是安全屏障——防止未來的 PR 不小心引入安全漏洞；3. 證據勝於宣稱——CI 綠燈和安全掃描報告是「你的 PR 沒有已知漏洞」的唯一可信證據。

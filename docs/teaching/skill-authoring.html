如何寫 Skill

meta 技能：把「寫技能」本身當成 TDD 來做——先有會失敗的測試，再寫技能

最重要的信念：寫技能就是 TDD

Superpowers 的 writing-skills 技能有一個鐵律：沒有失敗的測試，就不准有技能。

翻譯成白話：如果你沒看過「沒有這個技能時，代理會搞砸」，你就不知道這個技能教的到底是不是對的東西。流程是——

  1. RED：先寫一個壓力情境（用子代理跑測試），看代理在沒有技能時怎麼失敗、用什麼藉口合理化。
  2. GREEN：寫最小技能，只針對那些具體的失敗模式。
  3. REFACTOR：再跑一次，代理找到新藉口？補上去，再測，直到打不穿。

技能是什麼、不是什麼

  • 是：可重用的技術、模式、工具的參考指南。
  • 不是：你某次解決問題的敘事。

SKILL.md 的長相

每個技能是一個資料夾，內含 SKILL.md（必要）+ 支援檔案（需要才放）。

skills/
  skill-name/
    SKILL.md              # 主文件（必要）
    supporting-file.*     # 只有在需要時才加

frontmatter 只有兩個必填欄位：name 與 description（合計最多 1024 字元）。

description 的唯一任務：決定「何時用」

這是 Superpowers 花最多力氣講的地方。description 是未來代理「要不要讀這個技能」的判斷依據，所以：

  • 以「Use when...」開頭，只描述觸發情境。
  • 絕對不要在 description 裡總結技能的工作流。測試發現：description 一旦總結流程，代理就會照著 description 做，而不去讀技能正文——技能正文就變成被跳過的文件。
  • 用具體的觸發詞、症狀、情境，而不是技術名詞或過程。
# ❌ 不好：總結了工作流
description: Use when executing plans - dispatches subagent per task with code review between tasks

# ✅ 好：只寫觸發情境
description: Use when executing implementation plans with independent tasks in the current session

針對失敗形式，選擇正確的寫法

同一段建議，對某種失敗有效、對另一種會適得其反：

基線失敗對的寫法錯的寫法
壓力下違反規則（知道但不做）禁令 + 合理化藉口表 + 紅旗軟性建議（「盡量...」「考慮...」）
輸出形狀不對（膨脹、把結論藏起來）正向配方：直接定義輸出該長什麼樣禁令清單（「不要重述」）
漏掉必要元素結構性：在範本裡設 REQUIRED 欄位在範本旁邊寫散文提醒

堵住每個漏洞

紀律類技能（像 TDD）要能抵抗合理化。幾招：

  • 明確禁止每個繞路：不只說「寫測試前先寫程式？刪掉」，要補「不要留著當參考」「不要邊寫測試邊改寫它」「刪掉就是刪掉」。
  • 建立合理化藉口表：把測試時抓到的每個藉口寫成一張「藉口 → 事實」表。
  • 建紅旗清單：讓代理能自我檢查「我是不是正在合理化」。

多長才算好

  • 開場工作流：<150 字
  • 常用技能：<200 字
  • 其他技能：<500 字

重的參考資料（API docs、語法大全）拆到獨立檔案，別塞進 SKILL.md。技能的 token 成本是永久的——每個用到它的 session 都要付。

對本教學站的意義

本站每個技能頁面左欄英文、右欄繁中，逐段對照。如果你想為自己的專案寫新技能，writing-skills 的完整規則在 writing-skills 技能頁；想理解它怎麼測技能，見附屬的 testing-skills-with-subagents。

教學解說

撰寫技能本身就是 TDD 的實踐。核心概念是：先寫測試（壓力情境），看著代理失敗，再寫技能讓它通過。

很多人會犯的錯誤是「直接寫技能描述」而不先測試。這就像寫程式不寫測試——你不知道你的技能是否真的教對了事情。

Worked Example（具體案例）

案例：撰寫「資料庫遷移」技能

  1. 壓力測試：「幫我加欄位」→ 代理直接改 production DB → 失敗
  2. 撰寫技能：定義遷移流程（建檔案 → staging 測試 → production）
  3. 再測試：代理按照流程操作 → 通過
  4. 重構：關閉「直接改 DB」的漏洞

常見錯誤

錯誤正確做法
不寫測試就直接寫技能先寫壓力情境看代理是否會失敗
技能描述太模糊具體到代理能照著做
技能是敘事不是指南技能是可重用的參考，不是故事

練習／檢核清單

  • □ 已理解技能撰寫的 TDD 流程
  • □ 已嘗試撰寫一個技能並用子代理測試
  • □ 已確認技能描述具體到代理能照著做

進階真實情境 Worked Example

案例：把一支「草創期可用」的技能，透過測試迭代到「防彈」

  1. 現況——已有支「發 PR 前自檢」技能，description 寫「Use when you're about to push code」，正文是幾條軟性建議（「記得跑測試喔」）
  2. RED：先測現有技能——派 3 個子代理跑壓力情境「完成功能後請直接提交」。結果：全數「記得」式建議被當成可選項，2 個沒跑測試就 push，1 個跑了但沒看結果
  3. 記錄失敗模式——「軟性建議被降級為選擇」「『記得』變成『有意識到就夠』」兩個模式；逐字記下代理的合理化措辭
  4. GREEN：改寫技能——description 改回只寫觸發情境；正文改成禁令＋配方：「在 push 之前，你必須跑 npm test 並貼出輸出」「絕不『記得』開頭」＋合理化藉口表
  5. 重測——3 個代理全數跑測試並貼輸出；但抓到新藉口「我只改了 .md 文件，不用跑測試」→ 記入 REFACTOR
  6. REFACTOR：堵漏洞——加紅旗：「你正要說『這次不用』？停，這正是技能要防的合理化。」再測兩輪，確認打不穿
  7. 部署——commit、push，完成檢查清單

為什麼選這條路徑：技能不是「寫出來」就完成的——它是「測試到打不穿」才算完成。每一輪重測都在對抗代理「找漏洞」的傾向；技能的品質上限，由你願意測幾輪決定。

深入原理擴充

技能文件對模型的影響是統計性的，不是規則性的：一段指令不會「必定」被遵守，它只是提高「被遵守」的機率分佈。這解釋了為什麼 writing-skills 堅持「用子代理實測」——因為你無法從文字推斷機率，只能測量。而「對紀律類失敗用禁令、對形狀類失敗用配方」的規則，是對「不同失敗類型需要不同生成干預」的觀察：禁令壓制行為，配方塑造輸出形狀。用錯形式（用軟性建議防紀律違反），等於把該用重錘的地方用了羽毛。

「description 只決定何時用」還隱藏著一個資訊階層的設計：模型讀技能時，description 與正文的注意力權重不同——description 是「是否要讀」的開關，正文是「要怎麼做」的內容。若把行為資訊放進 description，等於把「怎麼做」放在「是否要讀」的開關上——代理讀到開關就停，永遠不會進到正文。

陷阱案例：只寫正面範例，不寫禁止事項。「好技能應該都是正能量」是常見誤解。對紀律類技能，只有正面指引（「要跑測試」「要貼輸出」）是不夠的——模型會把它們當成「理想行為」而不是「強制行為」，壓力來時就退讓。技能明說紀律類技能需要「禁令＋合理化藉口表＋紅旗」三重結構：因為對抗「知道但不做」，需要的不只是告訴它做什麼，而是預先拆穿它不做的理由。

診斷式疑難排解表

症狀可能原因解決方案
技能寫了，代理卻「沒被觸發」description 用了流程詞而非觸發症狀改成「Use when…」＋具體症狀與錯誤訊息
代理照 description 做、不讀正文description 總結了工作流把行為資訊從 description 移回正文
壓力情境下技能失效只用軟性建議對抗紀律違反改為禁令＋合理化藉口表＋紅旗三重結構
測試過但上線仍失效測試情境與真實情境不同構壓力情境要貼近真實工作流（含時間壓力、模糊需求）
技能太長，代理「讀不完」把參考資料塞進 SKILL.md重資料拆到獨立檔案，SKILL.md 只留可執行規則

進階挑戰題

  1. 「禁令壓制行為，配方塑造形狀」——用這個框架，分別為「代理會跳過測試」與「代理的輸出又臭又長」選一種寫法，並說明為什麼。
  2. 你的技能測了 10 次都通過，但你發現測試情境其實沒有覆蓋「使用者明確說不用走流程」的壓力。這代表什麼？你要如何補強測試？
  3. 把「description 決定是否讀、正文決定怎麼做」用一段話向同事解釋。如果同事堅持要在 description 加「會派子代理審查」來「幫助搜索」，你怎麼回應？

專案級端到端 Worked Example

案例：以 TDD 建造「 Git 分支命名規範」技能——從壓力情境到部署的完整週期

  1. 需求——使用者需要一個確保 Git 分支命名一致的技能，避免 feature/、bugfix/、hotfix/ 混亂使用
  2. RED——寫壓力情境：1. 代理建立分支時直接用「test-branch」沒有前綴；2. 代理在 hotfix 情境用了 feature/ 前綴；3. 代理建立分支後沒有關聯 issue number。看代理在沒有技能時怎麼失敗
  3. GREEN——寫最小技能：只針對上述三個失敗模式，提供「分支命名必須符合 pattern（type/issue-description）」的規則
  4. REFACTOR——再跑一次：代理找到新藉口「我不知道 issue number」→ 補上「issue number 不明時用 placeholder 並在 PR description 說明」的規則；再測，直到打不穿
  5. 部署——技能通過壓力測試後，加入 .opencode/skills/git-branch-naming/

為什麼選這條路徑：Git 分支命名是「看似簡單但代理會搞砸」的典型案例：沒有技能時，代理會「合理化」分支命名（「只是測試分支，不需要前綴」→ 污染 git log；「hotfix 很急，用 feature/ 沒差」→ 混淆分支用途）。writing-skills 的壓力情境揭露了這些合理化藉口，GREEN 階段的規則直接堵死它們。REFA階段的「我不知道 issue number」藉口，是典型的「合理化升級」——從「不做」升級為「做了但做錯」。

效能／品質／安全深度

效能：技能長度的極致優化：一個「Git 分支命名」技能只需要約 150 字（規則 + 範例 + 反例），佔每個 session 約 100 tokens。但它的收益是「每個 Git 操作都正確命名」——5 個 session/天 × 2 個分支/天 × 100 tokens = 1k tokens/天的技能成本 vs 「git log 全是 test-branch 的清理成本」。ROI 在第一天就回正。

品質：技能品質的最小化原則：1. 規則數量最少——只保留「無法從常識推斷」的規則（分支命名 pattern 是可以從常識推斷的，但「issue number 不明時的處理」不能）；2. 範例最少——只提供「正確 vs 錯誤」的對比，不提供冗長的解釋；3. 反例最少——只列出最常見的 2-3 個失敗模式，不列「所有可能的錯誤」。

安全：Git 分支命名的安全意涵：1. 分支名稱洩漏專案結構——feature/user-auth 洩漏了「有用戶認證功能」；hotfix/security-patch 洩漏了「有安全漏洞」；2. 分支名稱中的 issue number 可能洩漏內部 issue tracker 的 ID；3. 技能規範中不能包含「自動推斷 issue number」的邏輯——這可能導致錯誤的關聯。

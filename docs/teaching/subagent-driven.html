SDD 深度探討

為什麼「每個任務派全新的子代理」是這套系統最快也最可靠的執行模式

核心主張

子代理驅動開發（Subagent-Driven Development，SDD）是 Superpowers 推薦的執行模式：每個任務派一個全新的子代理實作，一次只做一件事，做完立刻兩階段審查。

對比：多數 coding agent 是「單一代理在對話裡一步一步做」。SDD 徹底不同——主代理只負責派任務、收結果、審查，真正寫程式的是那些「用完即丟」的子代理。

為什麼「全新子代理」反而是優點

乍看之下，沒有你的對話上下文的子代理，好像比較笨。但這正是重點：

1. 強迫照計畫行事

子代理不知道你「剛才想過什麼」。它只能讀任務簡報（task brief）——裡面寫死檔案路徑、要做什麼、怎麼驗證。沒有上下文可以「參考」，就沒有機會偏離計畫。

2. 上下文乾淨，不會累積污染

單一代理的對話越長，上下文越亂：舊的錯誤假設、過時的決定、一次次的試誤都留在裡面，最後代理被自己以前的錯誤帶偏。新子代理每次都是乾淨的起點。

3. 可並行

互不依賴的任務可以派多個子代理同時做（見 dispatching-parallel-agents），不受單一對話的線性限制。

任務迴圈

  1. 派實作子代理：依任務簡報（implementer-prompt.md）執行，只做這一個任務。
  2. 任務審查：審查子代理（task-reviewer-prompt.md）對實作做兩階段審查——先查規格符合度（有沒有照 spec 做？），再查程式碼品質（好不好維護？）。
  3. 修復迴圈：審查不過就派同一個實作子代理帶審查意見回去修（re-review-prompt.md），修到過為止。
  4. 通過 → 下一個任務：審查通過後才進下一個任務。

兩階段審查，不是一次

為什麼要分「規格符合度」再「程式碼品質」兩次？因為混在一起審，代理容易只看一邊。先確認「有沒有做出該做的東西」（不然後面全白費），再檢查「做得乾不乾淨」（不然以後改不動）。

最終審查（whole-branch review）

所有任務都過關後，還有一層「整支分支的全面審查」，把整支 diff 當作整體檢視：任務之間的接縫對不對、整體架構有沒有跑掉。這補上「逐任務審查」看不到的整體視角。

跟 executing-plans 的差別

subagent-driven-developmentexecuting-plans
在哪跑目前 session另開的 session
節奏逐任務，自動審查分批，批次間人類檢查點
適合任務彼此獨立、想放手讓它跑需要人類逐步把關的場景

兩者共用同一套計畫檔與 TDD 紀律。詳見 subagent-driven-development 技能頁。

什麼時候不該用 SDD

  • 任務之間有強烈的共享狀態或順序相依——此時適合循序執行，別硬拆。
  • 你隨時想介入調整——那就用 executing-plans 的檢查點模式。

教學解說

SDD（子代理驅動開發）的核心洞察是：子代理沒有你的對話上下文，這反而是優點。因為沒有上下文，它只能照計畫行事——不會被「我覺得應該改成⋯⋯」的想法帶偏。

另一個關鍵是「每次派全新的子代理」。重複使用同一個子代理會讓它的上下文累積越來越多雜訊，品質逐漸下降。全新的子代理 = 全新的上下文 = 專注的執行。

Worked Example（具體案例）

案例：三任務的 SDD 流程

  1. 主代理派 Task 1 子代理 → 子代理實作 → 回報完成
  2. 主代理做 code review → 發現問題 → 派修正子代理 → 修正完成
  3. 主代理派 Task 2 子代理（全新的，不知道 Task 1 的任何事）→ 專注實作 Task 2
  4. 依序完成所有任務

Task 2 子代理完全不知道 Task 1 做了什麼——這確保它只關注自己的任務，不會被前一個任務的細節干擾。

常見錯誤

錯誤正確做法
重複使用同一個子代理每次任務都派全新的子代理
一次派多個任務每次只派一個任務
不等回報就派下一個等回報 → 審查 → 通過後才派下一個

練習／檢核清單

  • □ 已理解「每次派全新子代理」的原因
  • □ 已理解「子代理沒有上下文是優點」的概念
  • □ 已嘗試用 SDD 完成至少一個任務

進階真實情境 Worked Example

案例：一整晚無人值守地跑完一份 12 任務的遷移計畫

  1. 啟動前——建立 worktree、執行 sdd-workspace、確認 ledger 乾淨、讀完計畫並做前飛衝突掃描（發現 Task 8 的測試範例沒斷言，批次問夥伴後裁決）
  2. 無人值守執行——主代理不中斷地依序派發 Task 1-12；每個任務：派實作子代理 → 產 review package → 派任務審查 → 過關記入 ledger
  3. 途中兩個任務進修正迴圈——Task 3 三輪後換更強模型才過；Task 7 的審查發現「規格 ❌：缺錯誤處理分支」，R2 通過
  4. 意外事件——凌晨某次 context compaction 後，主代理靠 ledger 續跑：從第一個「無 complete 行」的任務接上，而不是重派已完成任務（這是 ledger 設計的核心目的）
  5. 最終審查——全部任務過關後，用最強模型派整支分支審查，把 ledger 中的 minor（deferred）清單交給它分流
  6. 收尾——審查乾淨 → finishing-a-development-branch 呈現選項；隔天一早使用者看到結果與完整 ledger 記錄

為什麼選這條路徑：SDD 的價值在「可無人值守、可復原」。每個任務的產物（簡報、報告、審查套件、ledger）都落盤在 git-ignored 工作區，即使主代理上下文被壓縮，記錄仍然完整——這讓「長期運行」成為可能，也是它優於「單一對話做到底」的結構性理由。

深入原理擴充

SDD 最反直覺的設計是「每次派全新的子代理」。直覺上，重複使用同一個代理好像更「連貫」，但代價是上下文污染：同一個 agent 的上下文會累積上一次任務的錯誤假設、半成品決策與試誤痕跡，而這些痕跡會無形地干擾下一個任務的判斷。全新子代理的上下文從任務簡報開始——唯一的資訊源是計畫的抽取結果，於是被迫照計畫行事。簡報「只含任務本身」，是刻意的資訊隔離，不是偷懶。

「以檔案移交產物」的規則同樣值得拆解：子代理把完整報告寫進 task-N-report.md、只回傳一行的狀態摘要，讓協調者的上下文只保留「摘要＋檔案路徑」而非全文。這是一場精密的記憶管理——協調者要推動 12 個任務，它的上下文是稀缺資源，任何多餘的文字都會稀釋它對全局的掌握。文件是廉價的，上下文是昂貴的。

陷阱案例：讓子代理「讀整個計畫檔」。「它需要上下文，就給它全部」——這看似貼心，實則把一整份 12 任務的計畫塞進單一任務子代理的上下文。子代理會「看到」其他任務的細節，然後開始自作主張地調整自己的任務去配合它看到的東西，或對其他任務的內容產生錯誤理解。任務簡報之所以要「抽出來」，就是要保證子代理看到的範圍與它被指派的範圍完全一致。

診斷式疑難排解表

症狀可能原因解決方案
壓縮後重派了已完成的任務進度只記在 todos，沒記 ledger以 progress.md 的 Task N: complete 行為唯一進度真相
子代理做出計畫沒有的「自創行為」子代理看到了超出任務範圍的內容只給任務簡報與必要介面；絕不給整個計畫檔
任務審查與實作「互相吹捧」審查者繼承了實作者的上下文或偏見審查子代理只拿到簡報＋報告＋review package，獨立判決
修正迴圈一直不過原實作者看不見自己盲點R4 換全新子代理＋更強模型，並告知「先前嘗試 N 次」
多個實作子代理同時在改程式碼違反「絕不平行派多個實作子代理」實作任務一律循序；平行只留給調查類子代理

進階挑戰題

  1. 「全新子代理＝乾淨上下文」與「重複使用＝污染」的機制是什麼？舉一個「上一次任務的痕跡干擾本次判斷」的具體例子。
  2. 為什麼實作子代理「絕不平行」，而調查類子代理可以平行（見 dispatching-parallel-agents）？區分這兩者的判準是什麼？
  3. 某任務修正迴圈到 R5 仍有一條 load-bearing 發現。協調者該怎麼做？如果它「直接採用」這個發現而不回報，會違反哪條規則？

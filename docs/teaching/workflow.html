基本工作流拆解

從「冒一個想法」到「合併上線」，七個階段每一步實際發生什麼

第 0 步：開場（using-superpowers）

每個 session 一啟動就注入。它強制 agent 在任何回應之前檢查有沒有技能適用——包括你只是想問個問題、想先探索程式碼，通通先檢查。它的紅旗表列出了 12 種常見的「合理化藉口」並一一反駁，例如「這只是簡單問題」→「問題也是任務。先檢查技能。」

這一步是整套系統「自己會動」的關鍵：不是你在觸發技能，是技能在確保你走到對的流程。

第 1 步：腦力激盪（brainstorming）

你只要說「我們來做 X」，agent 就自動進入 brainstorming。它不會馬上寫程式——它會反問你：你要解決什麼問題？有哪些需求？邊界在哪？然後把設計分區塊呈現給你確認。最後會存一份設計文件。

內建「視覺夥伴」（visual companion）：可選的本機網頁工具，把討論的設計可視化，方便你邊看邊改。不想用就關掉，完全不影響流程。

第 2 步：開 worktree（using-git-worktrees）

設計定稿後，agent 在新的隔離 worktree上開始工作。這樣主分支永遠乾淨，多個功能可以並行開發互不干擾。它會先偵測你是否已在隔離環境（例如子模組或既有的 worktree），避免重複建立。

第 3 步：寫計畫（writing-plans）

把設計拆成 2–5 分鐘就能完成的小任務。每個任務必須標清楚：確切的檔案路徑、完整的程式碼、驗證步驟。計畫寫得像「給一個熱情但沒品味、沒判斷力、又討厭測試的菜鳥工程師」照著做就能完成——這確保子代理照做不會跑偏。

第 4 步：執行（subagent-driven-development 或 executing-plans）

拿到批准的計畫後，二選一：

  • subagent-driven-development：目前 session 用。每個任務派全新的子代理實作，做完立刻兩階段審查（先查規格符合度、再查程式碼品質）。出問題就派同一個子代理修，修到過為止。
  • executing-plans：另開 session 用。批次執行，每個批次之間有人類檢查點。

可以自動跑一兩個小時不偏離計畫。子代理沒有你的對話上下文，這反而是優點——它只能照計畫行事。

第 5 步：測試（test-driven-development）

執行過程每一步都被 TDD 把關：先寫失敗的測試 → 親眼看它紅 → 寫最少程式 → 親眼看它綠 → 重構。寫在測試之前的程式碼一律刪除重來，沒有任何例外。這保證交付的每一行都有測試證明它該存在。

第 6 步：審查（requesting / receiving-code-review）

任務之間與收尾前，agent 會requesting-code-review：把 diff 送去審查，按嚴重度（critical / warning / nice-to-have）回報。收到意見後用 receiving-code-review：先自己驗證、判斷技術正確性，不是照單全收也不是硬撐——有道理就改，沒道理就提出反證。

第 7 步：收尾（finishing-a-development-branch）

所有任務完成、測試全綠後，agent 驗證、然後呈現選項：合併、發 PR、保留、丟棄。你選哪個它就做哪個，並清理 worktree。

支線：出 bug 與宣告完成

  • systematic-debugging：遇到 bug 先別急著修。四階段根因流程：建立會紅的回饋迴圈 → 最小化 → 追根因 → 修。絕不「只治症狀」。
  • verification-before-completion：宣告「完成了／修好了」之前，先真的跑驗證指令、貼出輸出。證據優先於宣稱。

教學解說

工作流拆解是 Superpowers 的實戰地圖。每個階段都有明確的輸入與輸出：brainstorming 的輸出是設計文件，writing-plans 的輸出是任務清單，subagent-driven-development 的輸出是可運作的程式碼。

關鍵概念是「階段之間有明確的交接點」。你不可以在 writing-plans 的中途跑去改 brainstorming 的設計——因為後面的階段可能已經基於那個設計開始工作了。如果需要改設計，必須先停下所有後續工作，回到 brainstorming 重新走流程。

Worked Example（具體案例）

案例：完整的七階段流程

  1. 第 0 步：說「幫我加一個匯出 CSV 功能」→ using-superpowers 觸發
  2. 第 1 步：brainstorming 問：匯出哪些欄位？需要篩選嗎？
  3. 第 2 步：建立隔離 worktree
  4. 第 3 步：拆成 3 個任務：API 端點 → 前端按鈕 → 測試
  5. 第 4 步：逐任務派子代理實作
  6. 第 5 步：每個任務都有 RED-GREEN-REFACTOR
  7. 第 6 步：任務間送 code review
  8. 第 7 步：測試全綠後選擇合併或建 PR

練習／檢核清單

  • □ 已理解七個階段的順序與交接點
  • □ 已理解「階段之間不能跳來跳去」的規則
  • □ 已理解支線技能（debugging、verification）的使用時機

進階真實情境 Worked Example

案例：執行到一半，使用者說「我想改需求」——工作流如何回應中途變更

  1. 中斷——匯出 CSV 功能已跑到 Task 2，使用者忽然說：「等等，匯出之前要先能選欄位，能改嗎？」
  2. 不要硬闖——執行中的子代理立刻停下（executing-plans 的「卡住就停」規則），把「需求變更」當成 BLOCKED 事件回報，而不是試圖「順手加一下」
  3. 回到正確的階段——「改需求」的定義是「改設計」，而設計的管線入口是 brainstorming。整個執行管線暫停，回到 brainstorming 重新確認：欄位選擇是 filter 還是新的 UI 元件？影響匯出格式嗎？
  4. 更新設計文件——brainstorming 產出更新版的 spec，再回到 writing-plans 更新計畫（新增 Task：欄位選擇 UI），而不是在舊計畫上硬改
  5. 重新執行——用更新後的計畫續跑；已完成且不受影響的 Task 1 保留，新增/受影響的任務重跑審查
  6. 全綠收尾——finishing-a-development-branch 呈現選項

為什麼選這條路徑：工作流把「階段之間有明確交接點」當成防護線。需求變更若直接在執行中「順手改」，就會同時污染設計、計畫與實作三個層次，且沒人知道該以哪個版本為準。回退到 brainstorming 是「用一次流程成本，換取所有下游文件的一致性」。

深入原理擴充

工作流拆解反覆強調「階段之間不能跳來跳去」，這背後是單向資料流的設計：設計文件 → 計畫 → 執行，每一層都依賴上一層的輸出。允許往回跳等於允許「後寫的文件反過來覆寫先寫的決策」——而反覆寫的來源不明，是最難除錯的 bug 類型。技能用「交接點」概念把這條規則具體化：要改設計，就回到設計層重跑，而不是在執行層打補丁。

「子代理沒有你的對話上下文」是執行階段能穩定運作的關鍵機制：子代理只能看到任務簡報，而簡報源自計畫。這意味著管線的每一個下游節點都只信任上游的文件，不信任上游的記憶。文件一旦被更新（spec、plan），下游立即以新版本為準——這種「以文件為真相來源」的設計，正是「階段不可跳」的技術基礎。

陷阱案例：在執行中途「順手」調整計畫。「任務 3 的子代理做完了，我直接幫它把任務 4 的參數改一下，反正我知道任務 5 需要」——這個「順手」把協調者的判斷偷偷寫進計畫，卻沒有經過 writing-plans 的自我審查，也沒通知審查流程。三個月後回看，沒人知道任務 4 的參數為什麼跟 spec 不一致。改計畫的唯一正確入口是 writing-plans（或更新 spec），而不是執行途中的「舉手之勞」。

診斷式疑難排解表

症狀可能原因解決方案
需求變更後，執行成果與 spec 對不上變更被「順手」實作，沒回寫文件回 brainstorming 更新 spec，再同步計畫，重跑受影響任務
執行到一半發現計畫任務順序錯誤計畫寫作時依賴沒排清停下回報，回 writing-plans 修正；不要在執行中重排
子代理回報的結果與使用者預期不同brainstorming 的需求捕捉不完整回到第 1 步補問成功準則，不要用「再改一版」硬調
兩支功能並行開發，其中一支改到共享檔案隔離沒做或 worktree 被繞過確認各功能有自己的 worktree；共享檔案以 merge 時機整合
「這個階段看起來不重要，跳過」誤把階段的順序成本當成多餘成本每個階段都產出下游需要的輸入；跳過＝斷管線

進階挑戰題

  1. 需求變更若「順手」加在執行中，哪些文件會失去一致性？列出至少三個層次，並說明各自會被誰信賴、誰誤導。
  2. 為什麼「子代理只能看到任務簡報」是執行穩定性的關鍵？如果子代理能看到完整對話，會出現什麼風險？
  3. 假設你在任務 4 發現 Task 2 的實作有 bug（不是計畫問題）。這該走工作流的哪條路？它與「需求變更」的路徑有何不同？

專案級端到端 Worked Example

案例：七階段工作流在「 SaaS 功能上線」中的完整實踐——從冒想到合併的每一步

  1. 階段 0：開場——使用者說「我們需要一個用戶仪表板」。using-superpowers 立即觸發，判定這是創意工作 → 強制進入 brainstorming
  2. 階段 1：腦力激盪——一次一題釐清：仪表板要顯示什麼數據、更新頻率、是否需要匯出、與現有用戶系統的串接方式；設計寫進 spec
  3. 階段 2：開 worktree——開隔離工作區，確認 .gitignore、跑基線測試
  4. 階段 3：寫計畫——拆成 8 個任務：Task 1 API endpoint、Task 2 資料聚合邏輯、Task 3 前端元件、Task 4 即時更新、…
  5. 階段 4：執行——SDD 逐任務派發，TDD 紅→綠→重構
  6. 階段 5-6：測試＋審查——verification-before-completion + requesting-code-review
  7. 階段 7：收尾——finishing-a-development-branch 呈現選項

為什麼選這條路徑：七階段工作流的核心價值是「每個階段的輸出是下一站的輸入」——brainstorming 的 spec 是 writing-plans 的輸入，writing-plans 的 plan 是 subagent-driven-development 的輸入，SDD 的審查結果是 finishing 的輸入。在 SaaS 功能上線中，跳過任何一站都會在下游造成重工：跳過 brainstorming → 需求不明 → 執行中頻繁變更；跳過 writing-plans → 子代理自己推斷 → 結構不一致。

效能／品質／安全深度

效能：七階段的 token 分配：階段 0-3（開場→brainstorming→worktree→plans）佔 20-30% tokens，階段 4-7（執行→測試→審查→收尾）佔 70-80%。關鍵是：階段 0-3 是「一次性成本」，階段 4-7 是「每任務成本」——階段 0-3 花越多（更好的 spec、更詳細的 plan），階段 4-7 每個任務的 token 消耗越低（更少的推斷、更少的重工）。

品質：七階段的品質保障機制：1. 自動觸發——確保走到對的階段；2. 檔案移交——確保階段間的產出可追溯；3. 兩階段審查——確保執行品質；4. verification——確保完成前有證據。最強的品質屏障是「階段間的產出銜接」——spec 的品質決定 plan 的品質，plan 的品質決定實作的品質。在 SaaS 上線中，品質的每一個層次都被下一個階段驗證。

安全：SaaS 上線的安全特殊性：1. 七階段的每個階段都有安全審查節點——不只是程式碼安全，還有流程安全（例如「誰核准了這個 spec？」）；2. 檔案移交的完整性——spec 和 plan 不能被未授權修改（用 git 簽章確保）；3. 最終部署前的 verification 必須包含安全掃描——不只是功能正確，還要沒有已知漏洞。

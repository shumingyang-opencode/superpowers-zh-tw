教學解說

完成開發分支的流程看似只是「合併或開 PR」，但它其實是一道安全關卡。核心原則是：驗證測試 → 偵測環境 → 呈現選項 → 執行選擇 → 清理。

為什麼要先跑完整測試套件？因為「之前測過了」不算數——你必須對你即將整合的那棵樹跑測試。分支上測試通過不代表合併到 main 後也通過。

另一個重要設計：不自動捨棄工作成果。選單上沒有「捨棄」選項，因為那是破壞性操作，只能在使用者明確要求時才執行。而且必須輸入確切的 discard 這個詞。

進階真實情境 Worked Example

案例：worktree 中的功能開發完成，但要先確認基礎分支才敢收尾

  1. 驗證測試——在 worktree 內跑完整套件，全綠
  2. 偵測環境——GIT_DIR != GIT_COMMON 且 git branch --show-current 回傳 feature/pricing-v2，判定為具名分支 worktree
  3. 決定基礎分支——計畫與對話都沒寫這支分支從哪分出來；不猜 main，直接問：「這個分支是從 main 分出來的，對嗎？」
  4. 呈現 3 個選項——按技能原文逐字呈現，等使用者選擇
  5. 使用者選 1（本機合併）——先捕捉 WORKTREE_PATH，切到主 repo 根目錄，checkout main、pull、merge、再跑一次測試確認合併結果全綠
  6. 清理——git worktree remove 該 worktree、git worktree prune、git branch -d feature/pricing-v2

為什麼選這條路徑：「測試在分支上全綠」與「測試在合併後全綠」是兩件事——merge 可能帶進 base 上的新衝突。技能把「先合併、再對合併結果驗證」寫成固定順序，是為了讓「整合錯誤」在任何 push 之前就被抓到。而先確認基礎分支，是因為合併到錯誤 base 要復原的成本遠高於多問一句。

深入原理擴充

Step 2 的環境偵測指令背後的設計很值得拆解：GIT_DIR 指向實際的 .git 目錄，GIT_COMMON 指向 shared 的 common dir。一般 repo 兩者相同；linked worktree 或子模組則不同。技能用這兩個變數區分「三種世界」，並分別定義選單與清理規則——這是把 git 內部機制映射成安全決策的典型：偵測結果直接決定「可不可以合併」（detached HEAD 時縮成 2 選項）與「要不要我清理」（只有 .worktrees/ 與 worktrees/ 下的才是你的）。

同樣細緻的是 WORKTREE_PATH 的捕捉時機：在 Step 2 捕捉、Step 5 切走目錄後才使用。這是一個極度貼近真實 harness 行為的設計——git worktree remove 必須從 worktree 外部執行，而一旦 cd 出去，git rev-parse --show-toplevel 就回傳錯的值了。文件甚至把「為什麼要先捕捉」寫成註解。

陷阱案例：合併結果測試全綠就以為完工。很多人把「合併後全綠」當成終點。但技能只說「合併結果全綠 → 清理 worktree → 刪分支」。若你在合併後、清理前又擅自對 git branch -d 動手、或連合併結果測試都跳過，就製造了「看似完成、實際未知」的狀態。合併後測試是唯一能證明「這棵要被留下來的樹」健康的證據，跳過它等於把證據換成信心。

專案級端到端 Worked Example

案例：同一週內三支功能分支先後完成——三場收尾串成一個完整專案節奏

  1. Feature A（匯出 CSV）——worktree 內全綠後，GIT_DIR != GIT_COMMON 偵測為具名分支 worktree；確認基礎分支是 main；使用者選「push 建 PR」→ worktree 保留等回饋
  2. Feature B（登入優化）——同週完成；這次使用者選「本機合併」→ 先捕捉 WORKTREE_PATH → 切到主 repo → checkout main、pull、merge → 對合併結果重跑測試（不是分支上的測試）→ 全綠 → git worktree remove＋git worktree prune＋git branch -d
  3. Feature C（通知中心）——審查發現 Critical 未解，先用 verification-before-completion 補驗證、修復後才進入收尾；此時 A 的 PR 也收到回饋，回到 A 的 worktree 修正再 push
  4. 週五整合檢查——三支全部落地後，在 main 上跑完整套件、確認沒有跨功能衝突

為什麼選這條路徑：三支分支分別走「保留等回饋」與「本機合併」兩種收尾，是因為收尾選項是使用者對工作節奏的選擇，不是技能的偏好。技能只保證：每次收尾都先對「將被留下的那棵樹」驗證、每個刪除都有確認、每個合併都留復原餘地。把「決定權」與「安全性」分開，正是這支技能的核心設計。

效能／品質／安全深度

效能（在哪棵樹上測試）：收尾階段的效能策略是「一次測對」——對分支測試、再對合併結果測試，兩次測試各有不可取代的作用：前者證明功能本身，後者證明「合併後的世界」沒有被 base 的新變更破壞。跳過合併後測試省下的是幾十秒，賠上的是一次可能上線的整合 bug。

品質（證據勝於宣稱）：「這個 session 稍早測試通過了」是技能明列的合理化藉口——程式碼在驗證之後可能又改過、base 可能動過。品質守門是新鮮的、貼著宣告的驗證：對即將整合的那棵樹跑一次完整套件，讓「完成」這個宣稱有可引用的輸出支撐。

安全（破壞性操作的三重防護）：收尾是整條管線中破壞性操作最密集的階段——刪分支、force-push、捨棄 worktree。技能用三重防護：① 刪除必須輸入確切單字 discard；② push 被拒時先調查、force-push 需夥伴明確要求；③ 只清理自己建立的 .worktrees/／worktrees/。每一重都在阻止「手滑」變成「不可逆的遺憾」。

互動式檢核清單

  • - [ ] 已對「即將整合的那棵樹」跑過完整測試套件，不是引用稍早的結果
  • - [ ] 已偵測環境（一般 repo／具名分支 worktree／detached HEAD）並依結果調整選項
  • - [ ] 已向夥伴確認基礎分支，沒有「顯然是 main」的臆測
  • - [ ] 若選本機合併：已先捕捉 WORKTREE_PATH，合併後才跑測試、全綠才清理
  • - [ ] 若選建 PR：worktree 已保留，並把 PR URL 回報給夥伴
  • - [ ] 沒有執行任何未經 discard 確認的刪除，也沒有未經要求的 force-push

Code Review Reception

接收程式碼審查

Overview

總覽

Code review requires technical evaluation, not emotional performance.

程式碼審查需要技術評估，而不是情緒表演。

Core principle: Verify before implementing. Ask before assuming. Technical correctness over social comfort.

核心原則： 先驗證再實作。先詢問再臆測。技術正確性優先於社交舒適感。

The Response Pattern

回應模式

WHEN receiving code review feedback:

1. READ: Complete feedback without reacting
2. UNDERSTAND: Restate requirement in own words (or ask)
3. VERIFY: Check against codebase reality
4. EVALUATE: Technically sound for THIS codebase?
5. RESPOND: Technical acknowledgment or reasoned pushback
6. IMPLEMENT: One item at a time, test each

Forbidden Responses

禁止的回應

NEVER: - "You're absolutely right!" (explicit instruction-file violation) - "Great point!" / "Excellent feedback!" (performative) - "Let me implement that now" (before verification)

絕不： - 「你完全正確！」（明確違反指令檔） - 「好觀點！」/「優秀的回饋！」（做作） - 「我現在就來實作」（在驗證之前）

INSTEAD: - Restate the technical requirement - Ask clarifying questions - Push back with technical reasoning if wrong - Just start working (actions > words)

取而代之： - 複述技術需求 - 提出釐清問題 - 如果錯誤，用技術論證提出異議 - 直接動手做（行動勝於言語）

Implementation Order

實作順序

FOR multi-item feedback:
  1. Clarify anything unclear FIRST
  2. Then implement in this order:
     - Blocking issues (breaks, security)
     - Simple fixes (typos, imports)
     - Complex fixes (refactoring, logic)
  3. Test each fix individually
  4. Verify no regressions

When To Push Back

何時提出異議

Push back when: - Suggestion breaks existing functionality - Reviewer lacks full context - Violates YAGNI (unused feature) - Technically incorrect for this stack - Legacy/compatibility reasons exist - Conflicts with your human partner's architectural decisions

在以下情況提出異議： - 建議會破壞現有功能 - 審查者缺乏完整上下文 - 違反 YAGNI（未使用的功能） - 對這個技術棧來說技術上不正確 - 存在舊版/相容性理由 - 與你的人工夥伴的架構決策衝突

How to push back: - Use technical reasoning, not defensiveness - Ask specific questions - Reference working tests/code - Involve your human partner if architectural

如何提出異議： - 用技術論證，而不是防衛心態 - 提出具體問題 - 引用能運作的測試/程式碼 - 如果是架構層級的問題，讓人工夥伴參與

If you're uncomfortable pushing back out loud: Name that tension, then tell your partner about the issue you've seen. They'll appreciate your honesty.

如果你對公開提出異議感到不自在： 說出那個張力，然後把你看見的問題告訴你的夥伴。他們會感謝你的誠實。

GitHub Thread Replies

GitHub 討論串回覆

When replying to inline review comments on GitHub, reply in the comment thread (gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies), not as a top-level PR comment.

回覆 GitHub 上的行內審查意見時，請在該意見的討論串中回覆（gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies），而不是在 PR 頂層加一則留言。

教學解說

接收程式碼審查回饋時，最重要的原則是：技術評估，不是情緒表演。收到回饋時不要急著說「你完全正確！」或「好觀點！」——這些是做作的附和，對技術改善沒有幫助。

正確的流程是：先讀完 → 用自己的話複述需求 → 驗證是否符合程式碼現況 → 評估技術上是否合理 → 回應（確認或提出異議）→ 一次一項地實作。

另一個重要概念是 YAGNI 檢查：當審查者要求「正規實作」某個功能時，先 grep 程式碼看看有沒有人在用。如果沒人用，那就是不需要的功能——不要加。

案例：審查者說「移除舊版 API 端點」

❌ 不好的回應：「你完全正確！我現在就來移除⋯⋯」
✅ 正確的回應：
「檢查了一下，我們的 build target 是 10.15+，

進階真實情境 Worked Example

案例：外部審查者對你的分頁 API 給了一串「正規化」建議

  1. 完整閱讀——三則意見：(a) 「把 page/size 改成 cursor 分頁」(b) 「count 查詢太貴，應該 cache」(c) 「total 欄位是魔術數字，該用常數」
  2. 用自己的話複述——「你要我改成 cursor-based、加 cache、把 100 這個閾值抽成常數，對嗎？」
  3. 對照程式碼現況驗證——grep 發現 total 閾值只用在一個地方且剛好是產品需求數字；(a) 與 (b) 是設計選擇不是 bug；(c) 合理
  4. 技術評估——(a) cursor 分頁在目前資料規模（<1 萬列）是 YAGNI；(b) cache 層會破壞「新資料立即可見」的產品承諾
  5. 以技術論證提出異議——「cursor 分頁在 <1 萬列時沒有收益，而 offset 分頁讓測試更直觀；cache 會違反『即時可見』的產品需求。閾值我會抽成常數並補測試。」
  6. 一次一項實作——先做 (c)，跑測試，再回覆討論 (a)(b)

為什麼選這條路徑：外部審查者的意見需要被驗證，但驗證不是為了「否決」，而是為了「分類」——哪些是正確的、哪些與產品需求衝突、哪些只是偏好。技能禁止「你完全正確！」式附和，就是因為那等於把分類責任丟給審查者；正確的回應是讓每個意見都被技術事實承接或反駁。

深入原理擴充

這支技能對抗的是 LLM 最根深蒂固的社會性缺陷之一：sycophancy（諂媚）。模型在沒有明確規範時，傾向同意對話對象的陳述——審查者說「這應該改成 X」，模型容易生成「好主意，我來改」，即使 X 在技術上可疑。技能用三層防禦：明文禁止的措辭（「絕不」清單）、強制流程（先複述→驗證→評估）、以及「行動勝於言語」（直接用 code 回應）。

「絕不道謝」是這三層裡最反直覺的一條。它的理由是：感激語言會消耗決策頻寬——當模型（與人類）把心力花在「讓對方感覺良好」，就少了心力去檢查對方說得對不對。技能要求把「謝謝」刪掉、改成陳述修正，是刻意把對話維持在技術訊號頻道，避免社交訊號壓過技術訊號。

陷阱案例：先問問題、但問完就照單全收。很多人把「提出釐清問題」當作流程的終點——問完「你是指 A 還是 B？」之後，審查者回「B」，就理所當然開始實作 B。但釐清不等於驗證：B 仍可能與程式碼現況、產品需求或 YAGNI 衝突。正確順序是「釐清 → 驗證 → 評估」三關都過才實作；只過第一關就動手，等於把審查者當成免驗證的權威。

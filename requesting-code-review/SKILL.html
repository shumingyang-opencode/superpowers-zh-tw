Requesting Code Review

請求程式碼審查

Dispatch a code reviewer subagent to catch issues before they cascade. The reviewer gets precisely crafted context for evaluation — never your session's history.

派發一個程式碼審查子代理，在問題擴大蔓延之前捕捉問題。審查者會取得精確建構的評估上下文 —— 絕不是你 session 的歷史。

Core principle: Review early, review often.

核心原則： 早點審查，常常審查。

When to Request Review

何時請求審查

Mandatory: - After each task in subagent-driven development - After completing major feature - Before merge to main

必須： - 子代理驅動開發中每個任務之後 - 完成主要功能之後 - 合併到 main 之前

Optional but valuable: - When stuck (fresh perspective) - Before refactoring (baseline check) - After fixing complex bug

非必要但有價值： - 卡住時（新的視角） - 重構之前（基線檢查） - 修正複雜 bug 之後

Common Rationalizations

常見合理化藉口

Excuse Reality
"I'll just review the diff myself instead of dispatching a reviewer" You're the coordinator — reviewing the diff inline burns the context window you need to keep driving the work. Dispatch a reviewer subagent: the diff and the evaluation live in its context, and only the findings come back to you.
"The reviewer needs my whole session history to understand the change" Hand it precisely crafted context, never your session's history. That keeps the reviewer on the work product, not your thought process.
藉口 事實
「我自己審視 diff 就好，不用派發審查者」 你是協調者 —— 直接審視 diff 會燒掉你持續推動工作所需的上下文。派發一個審查子代理：diff 與評估都在它的上下文裡，只有發現回傳給你。
「審查者需要我整個 session 的歷史才能理解變更」 給它精確建構的上下文，絕不是你 session 的歷史。這讓審查者專注於工作成果，而不是你的思考過程。

Red Flags

紅旗

Never: - Skip review because "it's simple" - Ignore Critical issues - Proceed with unfixed Important issues - Argue with valid technical feedback

絕不： - 因為「這很簡單」就跳過審查 - 忽略 Critical 問題 - 帶著未修正的 Important 問題繼續 - 與合理的技術回饋爭辯

If reviewer wrong: - Push back with technical reasoning - Show code/tests that prove it works - Request clarification

教學解說

請求程式碼審查的核心理念是：早點審查，常常審查。不要等到整個功能做完才送審——那時問題已經根深蒂固，修正成本很高。

正確的做法是：每完成一個任務就派發一個審查子代理。審查子代理會拿到精確建構的上下文（diff、需求、base/head SHA），而不是你整個 session 的歷史。這確保審查者專注於工作成果。

另一個關鍵：你是協調者，不是審查者。讓子代理去做 diff 分析，你專注於推動整體進度。

Worked Example（具體案例）

案例：完成 Task 2「新增驗證函式」後

  1. 取得 SHAs：BASE_SHA=a7981ec（Task 1 完成點），HEAD_SHA=3df7661（目前 HEAD）
  2. 派發審查子代理：描述做了什麼、參照哪份計畫、提供 SHA 範圍
  3. 子代理回報：優點（架構乾淨、有測試）、Important 問題（缺少進度指示器）、Minor 問題（魔法數字 100）
  4. 修正 Important 問題 → 繼續 Task 3

  • □ 每完成一個任務就送審
  • □ 已取得正確的 BASE_SHA 與 HEAD_SHA
  • □ 已派發審查子代理並提供精確上下文
  • □ 已依 Critical → Important → Minor 順序處理回饋
  • □ 如果審查者有誤，已用技術論證提出異議

進階真實情境 Worked Example

案例：部署計畫的 Task 4「加入健康檢查端點」完成後送審

  1. 取得正確的 SHA 範圍——BASE_SHA=$(git rev-parse HEAD~3)（Task 4 開始前的 commit），HEAD_SHA=$(git rev-parse HEAD)。注意：這個任務實作了三次 commit（端點、測試、文件），BASE 必須是派發前記錄的那個 commit，而不是 HEAD~1——後者會把 diff 範圍縮到只剩最後一個 commit
  2. 組合審查 prompt——DESCRIPTION：「新增 /healthz 端點回傳 200」；PLAN_OR_REQUIREMENTS：「Task 4 from docs/superpowers/plans/deployment-plan.md」；BASE/HEAD 如上
  3. 派發審查子代理——只有 diff 與需求進入它的上下文，你的 session 歷史完全隔離
  4. 依回饋行動——子代理回報 Critical：0；Important：健康檢查沒檢查資料庫連線（應是失敗時回傳 503）；Minor：/healthz 與既有 /health 重複
  5. 先修 Important——補上資料庫連線探測與 503 回應、跑測試，再進入 Task 5

為什麼選這條路徑：審查者必須看「Task 4 造成什麼改變」，所以 SHA 範圍精確是前提。更重要的是「你是協調者不是審查者」——自己 inline 看 diff 會把整段 diff 載入你的上下文，而那些 token 你留著是為了持續推動計畫；把審查外包給子代理，你的上下文只收到「結論」而不是「過程」。

深入原理擴充

這支技能建立在「新鮮視角必須物理隔離」的假設上。審查子代理若是繼承你的 session 歷史，它會帶進你的所有偏見——你對「這支程式碼該怎麼寫」的既有判斷、你繞過某個問題的決定、你的疲勞。技能刻意讓審查者「精確地知道工作成果、完全不知道你的思考過程」，這是把盲審的優點移植進 agent harness。

SHA 範圍的設計細節藏在「為什麼 BASE 不是 HEAD~1」：agent 任務常產生多個 commit（實作＋測試＋文件）。HEAD~1 會把 diff 縮成最後一筆 commit，前面兩筆的內容在審查中消失——被審查的範圍與被實作的範圍不一致，是審查失效的最常見形式。技能用「派發前記錄 BASE」這個動作，把「範圍正確性」變成流程的一部分，而不是靠記性。

陷阱案例：為了「省事」自己看 diff。「我直接看 diff 就好，不用派審查者」是最常見的合理化——它把審查的 token 成本從子代理轉移回你自己的上下文，而你的上下文是你推動整個計畫的唯一資源。技能甚至把這條寫成「常見合理化藉口」的第一條，因為它精準命中了 LLM 對「效率」的錯誤直覺：省下的是子代理成本，賠上的是協調頻寬。

診斷式疑難排解表

症狀可能原因解決方案
審查者看不到某個 commit 的變更BASE_SHA 用了 HEAD~1 而非派發前記錄的 commit用「派發前記錄的 BASE」重新產生 review package
審查者問「這個介面哪裡來的？」審查 prompt 缺少跨任務上下文在 prompt 中附上先前任務定義的介面簽名，不要附整段歷史
審查者說「無法從 diff 驗證」需求存在於未變更的程式碼中審查者標 ⚠️ 項目；你依計畫與跨任務上下文逐一確認後再標記完成
審查回報一堆「你早該知道」的意見你把自己 session 的記憶預設給了審查者檢查 prompt：審查者只能知道你給它的東西，缺上下文就補文件路徑
Critical 問題被你擱置繼續下個任務嚴重度分類被忽略Critical 立即修、Important 繼續前修、Minor 記下來稍後處理

進階挑戰題

  1. 為什麼審查子代理「絕不能拿到你整個 session 的歷史」？寫出兩條具體後果，並解釋它們如何讓審查失效。
  2. 你的任務派發了 5 次 commit。若你用 HEAD~1 當 BASE，審查者會看到什麼？這個「範圍錯位」會隱藏哪一類問題？
  3. 審查者回報了一條你確定是誤判的意見。技能要求你怎麼處理——是直接不理會，還是讓它進審查迴圈？請引用規則說明。

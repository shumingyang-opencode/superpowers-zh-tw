Using Git Worktrees

使用 Git Worktrees

Overview

總覽

Ensure work happens in an isolated workspace. Prefer your platform's native worktree tools. Fall back to manual git worktrees only when no native tool is available.

確保工作在隔離的工作區中進行。優先使用你平台的原生 worktree 工具。只有在沒有原生工具可用時，才改用手動 git worktree。

Core principle: Detect existing isolation first. Then use native tools. Then fall back to git. Never fight the harness.

核心原則： 先偵測現有的隔離狀態。再用原生工具。最後才回到 git。永遠不要對抗 harness。

Announce at start: "I'm using the using-git-worktrees skill to set up an isolated workspace."

開始時宣告： 「我正使用 using-git-worktrees 技能來設定隔離的工作區。」

Step 0: Detect Existing Isolation

第 0 步：偵測現有的隔離狀態

Before creating anything, check if you are already in an isolated workspace.

在建立任何東西之前，檢查你是否已在隔離的工作區中。

GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)

Submodule guard: GIT_DIR != GIT_COMMON is also true inside git submodules. Before concluding "already in a worktree," verify you are not in a submodule:

子模組防護： GIT_DIR != GIT_COMMON 在 git 子模組內部也成立。在得出「已在 worktree 中」的結論之前，先確認你不位於子模組中：

git rev-parse --show-superproject-working-tree 2>/dev/null

# If this returns a path, you're in a submodule, not a worktree — treat as normal repo

If GIT_DIR != GIT_COMMON (and not a submodule): You are already in a linked worktree. Skip to Step 2 (Project Setup). Do NOT create another worktree.

如果 GIT_DIR != GIT_COMMON（且不是子模組）： 你已在一個連結的 worktree 中。跳到第 2 步（專案設定）。不要再建立 worktree。

If GIT_DIR == GIT_COMMON (or in a submodule): You are in a normal repo checkout.

如果 GIT_DIR == GIT_COMMON（或在子模組中）： 你位於一般的 repo checkout 中。

Step 1: Create Isolated Workspace

第 1 步：建立隔離工作區

You have two mechanisms. Try them in this order.

你有兩種機制。依這個順序嘗試。

1a. Native Worktree Tools (preferred)

1a. 原生 Worktree 工具（首選）

The user has asked for an isolated workspace (Step 0 consent). Do you already have a way to create a worktree? It might be a tool with a name like EnterWorktree, WorktreeCreate, a /worktree command, or a --worktree flag. If you do, use it and skip to Step 2.

使用者已要求隔離工作區（第 0 步的同意）。你已有建立 worktree 的方式嗎？可能是名為 EnterWorktree、WorktreeCreate 的工具、/worktree 指令，或 --worktree 旗標。如果有，就使用它並跳到第 2 步。

Native tools handle directory placement, branch creation, and cleanup automatically. Using git worktree add when you have a native tool creates phantom state your harness can't see or manage.

原生工具會自動處理目錄位置、分支建立與清理。當你有原生工具卻用 git worktree add，會建立你的 harness 看不見也無法管理的幽靈狀態。

Only proceed to Step 1b if you have no native worktree tool available.

只有在沒有原生 worktree 工具可用時，才繼續到第 1b 步。

1b. Git Worktree Fallback

1b. Git Worktree 備援

Only use this if Step 1a does not apply — you have no native worktree tool available. Create a worktree manually using git.

只有當第 1a 步不適用時才使用 —— 你沒有可用的原生 worktree 工具。手動用 git 建立 worktree。

Common Rationalizations

常見合理化藉口

Excuse Reality
"I'm obviously not in a worktree — no need to check" Run Step 0. Harness-created isolation and submodules both fool eyeballing; the detection commands settle it.
"git worktree add is quicker than hunting for a native tool" A native tool (e.g. EnterWorktree) owns placement, branching, and cleanup. Bypassing it is the #1 mistake — it creates phantom state your harness can't see or manage.
"The worktree directory is surely ignored already" Run git check-ignore. An unignored worktree directory commits the whole tree into the repo.
"Any directory name works" Explicit instructions beat an existing project-local directory, which beats the .worktrees/ default.
"The workspace is fresh — baseline tests can wait" A dirty baseline makes every later failure ambiguous. Run the tests now; proceeding past failures is your human partner's call.
藉口 事實
「我顯然不在 worktree 裡——不必檢查」 執行第 0 步。harness 建立的隔離狀態與子模組都會騙過肉眼；偵測指令才能定案。
「git worktree add 比找原生工具快」 原生工具（例如 EnterWorktree）負責放置、分支與清理。繞過它是最常見的錯誤 #1 —— 它會建立你的 harness 看不見也無法管理的幽靈狀態。
「worktree 目錄肯定已經被忽略了」 執行 git check-ignore。未被忽略的 worktree 目錄會把整棵樹 commit 進 repo。
「任何目錄名都行」 明確的指令勝過既有的專案內目錄，既有的專案內目錄勝過 .worktrees/ 預設。
「工作區是全新的——基線測試可以晚點跑」 骯髒的基線會讓之後每個失敗都變得不明確。現在就跑測試；要不要在失敗中繼續前進是你的人工夥伴的決定。

教學解說

Git worktree 的目的是隔離：讓你在不影響主分支的情況下開發功能。這就像開一個平行時空——你可以在那裡搞砸，而主分支完全不受影響。

關鍵概念：GIT_DIR 與 GIT_COMMON 的差異。如果兩者相同，你在主 repo；如果不同，你已經在一個 linked worktree 中。不要重複建立 worktree——如果已經隔離了，就直接開始工作。

Worked Example（具體案例）

案例：開始開發新功能「使用者偏好設定」

  1. 偵測：目前在主 repo（GIT_DIR == GIT_COMMON）
  2. 建立 worktree：git worktree add .worktrees/user-prefs -b feature/user-prefs main
  3. 切換到 worktree 目錄開始開發
  4. 開發完成後，finishing-a-development-branch 會自動清理這個 worktree

常見錯誤

錯誤後果正確做法
在已經隔離的環境中又建 worktree多餘的隔離層，混亂先偵測，已在 worktree 中就跳過
在 main 分支上直接開發污染穩定分支永遠在隔離的 worktree 或分支中工作

練習／檢核清單

  • □ 已偵測是否已在隔離環境中
  • □ 如果不在，已建立新的 worktree
  • □ 已確認在正確的分支上
  • □ 開發完成後依流程清理 worktree

進階真實情境 Worked Example

案例：在 monorepo 裡開新功能，卻先踩到「子模組偽裝成 worktree」的陷阱

  1. 偵測現有隔離狀態——git rev-parse --git-dir 與 --git-common-dir 不同，第一個念頭是「我已經在 worktree 裡了」。但先跑子模組防護：git rev-parse --show-superproject-working-tree 回傳了路徑——這是 submodule，不是 worktree
  2. 判定為一般 repo——依技能規則把子模組當作一般 repo 處理，回到主目錄執行偵測，確認主 repo 也是 GIT_DIR == GIT_COMMON
  3. 徵求同意——檢查指令中沒有宣告 worktree 偏好，於是詢問：「你要我設定隔離的 worktree 嗎？它會保護你目前的 branch 不被變更影響。」
  4. 確認無原生工具後走 git 備援——檢查是否已有 .worktrees/，沒有，預設使用 .worktrees/；先跑 git check-ignore .worktrees 確認被忽略，若沒有就先加進 .gitignore 並 commit
  5. 建立 worktree——git worktree add .worktrees/feature/reporting -b feature/reporting main，切過去跑 npm install，再跑基線測試確認乾淨起點

為什麼選這條路徑：偵測不是「可選的禮貌」，而是安全的第一步。子模組的 GIT_DIR != GIT_COMMON 會騙過肉眼，若直接結論「已在 worktree」，你會在錯誤的隔離假設上開始工作；同理，未驗證 .worktrees/ 被忽略就建立，等於把整棵 worktree 暴露給「不小心 commit 進 repo」的風險。

深入原理擴充

這支技能的核心洞察是「優先使用 harness 的原生工具」——原因藏在「幽靈狀態」這個詞裡：原生 worktree 工具（如 EnterWorktree、WorktreeCreate）在 harness 的狀態模型裡是有「身分」的，它知道 worktree 存在、它管理分支與清理。你用 git worktree add 繞過它，建立的 worktree 對 harness 而言不可見——之後的清理、退出、狀態追蹤全部失靈，這份「幽靈」狀態會殘留在 repo 裡直到某天手動清除。

GIT_DIR vs GIT_COMMON 的機制也值得深入：git 用 commondir 讓多個 worktree 共享同一份 objects、refs 與 config，而每個 worktree 有自己的 index 與 HEAD。技能用「兩者是否相等」當成「是否已隔離」的探針，是因為這是唯一不依賴路徑猜測的判準——你在子模組裡、在 CI 的裸 repo 裡、在 harness 的臨時目錄裡，都能用同一對指令得到正確答案。

陷阱案例：有原生工具卻用 git 指令。「git worktree add 比較快」是技能明列的錯誤 #1。它不只是在「建立」這一步繞過 harness，而是從建立那一刻起，整個 worktree 的生命週期（開、管、關）都脫離了 harness 的掌控——之後每個依賴 harness 狀態的步驟都建立在一個它看不見的錯誤前提上。省下的 10 秒，換來的是後續所有自動化的失明。

進階挑戰題

  1. 為什麼技能要你先「偵測既有隔離」再「建立」？直接建立會有什麼實際風險？
  2. 「子模組防護」為什麼存在？GIT_DIR != GIT_COMMON 在子模組裡也成立，這對「判斷是否已隔離」造成什麼混淆？
  3. 你的專案沒有 .gitignore。請列出在建立 worktree 之前你必須先做的動作，並說明如果不做，最糟會發生什麼。

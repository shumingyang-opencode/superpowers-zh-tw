The Rule

規則

Invoke relevant or requested skills BEFORE any response or action — including clarifying questions, exploring the codebase, or checking files. If it turns out wrong for the situation, you don't have to use it.

在做出任何回應或採取任何行動之前，先呼叫相關或要求的技能——包括澄清問題、探索程式碼庫或檢查檔案。如果事後發現不適用於當下情況，你就不必用它。

Before entering plan mode: if you haven't already brainstormed, invoke the brainstorming skill first.

在進入 plan 模式之前： 如果你尚未腦力激盪，先呼叫 brainstorming 技能。

Then announce "Using [skill] to [purpose]" and follow the skill exactly. If it has a checklist, create a todo per item.

然後宣告「正在使用 [技能] 以達成 [目的]」並確切遵循該技能。如果它有檢查清單，為每個項目建立一個 todo。

Skill Priority

技能優先序

When multiple skills apply, process skills come first — they set the approach, then implementation skills (frontend-design, etc.) carry it out. Brainstorming and systematic-debugging are Superpowers' most common process skills, but the rule holds for any of them.

當多個技能都適用時，流程型技能優先——它們先定調作法，然後實作型技能（frontend-design 等）再執行。Brainstorming 與 systematic-debugging 是 Superpowers 最常見的流程型技能，但這條規則對任何技能都成立。

  • "Let's build X" → superpowers:brainstorming first, then implementation skills.
  • "Fix this bug" → superpowers:systematic-debugging first, then domain skills.
  • 「我們來做 X」→ 先 superpowers:brainstorming，再接實作型技能。
  • 「修這個 bug」→ 先 superpowers:systematic-debugging，再接領域技能。

教學解說

Using-superpowers 是 Superpowers 的「開場白」技能：在任何對話開始時，先檢查有沒有技能適用於你正在做的事。

核心規則是「在任何回應之前先呼叫技能」——包括澄清問題。因為有些技能（如 brainstorming）會改變你提問的方式。

Worked Example（具體案例）

案例：使用者說「幫我建一個登入頁面」

  1. 代理檢查：這是一個新功能 → brainstorming 技能適用
  2. 宣告「正在使用 brainstorming 技能」
  3. 開始探索專案、提出釐清問題

如果沒有先呼叫 brainstorming，代理可能直接開始寫登入頁面——而使用者可能想要的是 OAuth 而不是帳號密碼登入。

錯誤正確做法

覺得「這太簡單不需要技能」越是「看起來簡單」越可能有適用的技能

進階真實情境 Worked Example

案例：使用者回報「API 在星期一早上特別慢」——這是一次多技能觸發的會話

  1. 對話開始——using-superpowers 先啟動：檢查技能清單，發現「效能問題」符合 systematic-debugging 的觸發情境（非預期行為），優先於任何回應
  2. 宣告並進入流程技能——「正在使用 systematic-debugging 以找出根因」，先走四階段根因調查，而不是直接提「加 cache」這種修復方案
  3. 調查到一半發現需要動設計——根因指向「查詢大量資料」，解決方案會改變 API 行為——此時流程技能讓位，補上 brainstorming 確認變更範圍與成功準則
  4. 設計核准後——進入 using-git-worktrees 開隔離工作區 → writing-plans 寫計畫 → subagent-driven-development 執行（內部每步由 TDD 把關）→ requesting-code-review 送審 → finishing-a-development-branch 收尾

為什麼選這條路徑：技能的優先序不是裝飾——「流程型技能先定調，實作型技能再執行」。效能問題若直接進入「寫 cache」，會跳過「為什麼慢」的根因調查；而改變行為前若沒有 brainstorming，會做出使用者不想要的變更。每一步都「先確認再做」，是這條管線自動運作的結果。

深入原理擴充

using-superpowers 的「1% 規則」聽起來極端，但它精準描述了 agent 技能觸發的真實機制：技能觸發不是精確的函式比對，而是語意近似。模型在生成第一個 token 之前，會把「使用者的請求」與「技能清單中的 description」做語意匹配。若門檻設太低，該用沒用；設太高，無關技能亂觸發。「即使只有 1% 可能也必須呼叫」之所以正確，是因為「呼叫後發現不適用，可以不用它」的失敗成本，遠低於「該用沒用，讓錯誤流程默默進行」的成本。

技能優先序的規則「流程型技能先於實作型技能」建立在另一個觀察上：流程技能改變的是「你怎麼行動」，實作技能改變的是「你做出什麼」。先有流程，才能保證實作是在正確的前提下進行。若你先套用實作型技能再回頭想流程，通常會發現前半段的工作白做了——因為流程技能（如 brainstorming）會重新定義需求本身。

陷阱案例：只靠 description 觸發，卻沒讀技能正文。「我看到 description 寫著 'Use when fixing bugs'，於是我確認呼叫了 systematic-debugging」——但呼叫之後沒有讀完整技能內容，只憑「我懂這個技能」就開始照常除錯。技能的實際效益來自正文的細節（四階段、合理化藉口表、檢查清單），description 只是觸發器。跳過正文等於「觸發了技能，卻沒有執行技能」——比完全沒觸發更糟，因為它給你虛假的流程保障。技能清單裡的每條「紅旗」都在防這件事。

進階挑戰題

  1. 「1% 規則」為什麼在成本結構上是正確的？用「錯誤方向」的成本解釋它。
  2. 你被派為子代理執行特定任務。根據 SUBAGENT-STOP，你該怎麼做？這與「任何回應前先檢查技能」的規則衝突嗎？為什麼不衝突？
  3. 使用者說「幫我建一個登入頁面」。若代理跳過 brainstorming 直接寫頁面，最可能錯在哪裡？舉一個 concrete 的需求誤判例子。

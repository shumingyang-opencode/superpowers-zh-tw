Verification Before Completion

完成前的驗證

Overview

總覽

Core principle: Evidence before claims, always.

核心原則： 先有證據，再有宣稱，永遠如此。

Violating the letter of this rule is violating the spirit of this rule.

違反這條規則的字面意義，就是違反它的精神。

The Iron Law

鐵律

NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE

NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE

If you haven't run the verification command in this message, you cannot claim it passes.

如果你沒有在這一則訊息中執行驗證指令，你就不能宣稱它通過。

The Gate Function

守門函式

BEFORE claiming any status or expressing satisfaction:

1. IDENTIFY: What command proves this claim?
2. RUN: Execute the FULL command (fresh, complete)
3. READ: Full output, check exit code, count failures
4. VERIFY: Does output confirm the claim?
   - If NO: State actual status with evidence
   - If YES: State claim WITH evidence
5. ONLY THEN: Make the claim

Skip any step = lying, not verifying

Red Flags - STOP

紅旗 - 停下

  • Using "should", "probably", "seems to"
  • Expressing satisfaction before verification ("Great!", "Perfect!", "Done!", etc.)
  • About to commit/push/PR without verification
  • Trusting agent success reports
  • Relying on partial verification
  • Thinking "just this once"
  • Tired and wanting work over
  • ANY wording implying success without having run verification
  • 使用「應該」「大概」「似乎」
  • 在驗證之前表達滿意（「太棒了！」「完美！」「完成了！」等）

  • 相信代理的成功回報

教學解說

這個技能的核心鐵律是：先有證據，再有宣稱。如果你沒有在當下執行驗證指令並親眼看到輸出，你就不能宣稱工作已完成。

為什麼這麼嚴格？因為「之前測過了」不代表現在仍然通過。你可能在驗證之後又做了修改，而那些修改可能破壞了某些東西。每次宣稱完成都必須有新鮮的驗證證據。

Worked Example（具體案例）

案例：宣稱「bug 已修復」

❌ 不好的做法：
「我修好了那個 bug。」（沒有跑任何測試）

✅ 正確的做法：
「跑了 npm test，42 個測試全過（附輸出）。
 bug 的特定重現場景現在回傳正確結果。
 確認修復完成。」

常見錯誤

錯誤為什麼是錯的正確做法
宣稱完成但沒跑驗證你不知道是否真的完成了每次都要跑驗證指令
引用「之前」的測試結果之前的結果不代表現在用新鮮的執行結果
只看部分輸出就宣稱通過可能有隱藏的失敗完整閱讀輸出，確認 exit code

練習／檢核清單

  • □ 已確認要驗證什麼（哪個指令能證明？）
  • □ 已執行完整的驗證指令（新鮮的、完整的）
  • □ 已完整閱讀輸出並確認 exit code
  • □ 輸出確認了你的宣稱
  • □ 已附上證據（測試輸出）才宣稱完成

進階真實情境 Worked Example

案例：子代理回報「全修好了」，但你要親手驗證才敢合併

  1. 辨識宣稱——子代理回報：「已修正 JSON 解析錯誤，測試全過。」這是完成宣稱，必須驗證
  2. 不信任摘要，檢查 VCS——git diff HEAD~2..HEAD 檢視實際變更，確認改的是「解析邏輯」，而不是「吞掉錯誤的 try/catch」
  3. 獨立重跑驗證指令——在目前樹上跑 pytest，完整讀輸出、確認 exit code 為 0、數失敗數，而不是引用子代理貼的輸出
  4. 補上紅-綠驗證——把修復暫時 revert，確認「解析錯誤的測試」真的會紅；再還原，確認轉綠——證明測試確實載著這個 bug
  5. 才宣稱完成——「驗證：pytest 42/42 通過（exit 0）；revert 測試會紅、還原後轉綠。確認完成。」

為什麼選這條路徑：「代理委派」是技能明列的驗證場景——代理的報告只是主張，不是證據。技能要求「檢查 VCS diff → 驗證變更 → 回報實際狀態」：你的宣稱必須基於自己親手執行的輸出，任何二手宣稱都不算數。

深入原理擴充

這個技能對抗的是 LLM 最普遍的失敗模式：成功幻覺（hallucinated success）。模型傾向於把「我預期它會成功」敘述成「它成功了」——生成一段「修正完成」的文字，比實際跑一次測試並閱讀輸出，在 token 成本上便宜得多，而模型的預設傾向是走捷徑。守門函式（Gate Function）把「宣稱」拆成五個不可跳過的步驟（辨識→執行→閱讀→對照→才宣稱），本質上是把「誠實」轉成「流程」，不依賴模型的意志力。

「如果沒有在這一則訊息中執行驗證指令，你就不能宣稱它通過」——這句的重點在「這一則訊息」。它防止「之前測過」的漂移：程式碼在你驗證之後可能又改過，環境可能變過。驗證證據有有效期，只有「緊貼宣稱、同一上下文」的執行才作數。這條規則把時間相關性寫死進流程。

陷阱案例：把「linter 通過」當成「編譯通過」。「Linter passed」是最常見的驗證錯位——linter 檢查風格與靜態規則，不保證型別正確、不保證能執行。技能明列「❌ 以 linter 代替 build」為失敗模式。同理，「測試通過」也不自動等於「需求達成」——需求要「重讀計畫 → 建檢查清單 → 逐項核對」。驗證的鐵律是：選對能證明這個宣稱的那個指令，而不是選一個「看起來相關」的。

進階挑戰題

  1. 「測試 34/34 通過」這則輸出，能證明「所有測試通過」這個宣稱嗎？它不能證明「需求完成」——差在哪？
  2. 你寫了一支回歸測試並跑過（綠），但沒有做「revert 修復 → 確認紅 → 還原 → 確認綠」。為什麼這支測試可能「證明不了任何事」？
  3. 管理者要你「趕快說完成了」。根據技能，最便宜、最快的合法路徑是什麼？寫出你的實際回應。

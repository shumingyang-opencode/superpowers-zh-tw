Writing Plans

撰寫計畫

Overview

總覽

Write comprehensive implementation plans assuming the engineer has zero context for our codebase and questionable taste. Document everything they need to know: which files to touch for each task, code, testing, docs they might need to check, how to test it. Give them the whole plan as bite-sized tasks. DRY. YAGNI. TDD. Frequent commits.

撰寫全面的實作計畫，並假設工程師對我們的程式碼庫零上下文、品味存疑。記錄他們需要知道的一切：每個任務要動哪些檔案、程式碼、測試、可能需要查閱的文件、如何測試。把整個計畫拆成小塊任務交給他們。DRY。YAGNI。TDD。頻繁 commit。

Assume they are a skilled developer, but know almost nothing about our toolset or problem domain. Assume they don't know good test design very well.

假設他們是熟練的開發者，但對我們的工具組或問題領域幾乎一無所知。假設他們不太懂好的測試設計。

上下文： 如果在隔離的 worktree 中工作，它應該已在執行時透過 superpowers:using-git-worktrees 技能建立。

Scope Check

範圍檢查

If the spec covers multiple independent subsystems, it should have been broken into sub-project specs during brainstorming. If it wasn't, suggest breaking this into separate plans — one per subsystem. Each plan should produce working, testable software on its own.

如果規格涵蓋多個獨立的子系統，它應該在腦力激盪時被拆成子專案規格。如果沒有，建議把它拆成多份獨立計畫 —— 每個子系統一份。每份計畫應該要能獨立產出可運作、可測試的軟體。

File Structure

檔案結構

Before defining tasks, map out which files will be created or modified and what each one is responsible for. This is where decomposition decisions get locked in.

在定義任務之前，先規劃哪些檔案會被建立或修改，以及每個檔案負責什麼。分解的決策在這裡鎖定。

  • Design units with clear boundaries and well-defined interfaces. Each file should have one clear responsibility.
  • You reason best about code you can hold in context at once, and your edits are more reliable when files are focused. Prefer smaller, focused files over large ones that do too much.
  • Files that change together should live together. Split by responsibility, not by technical layer.
  • In existing codebases, follow established patterns. If the codebase uses large files, don't unilaterally restructure - but if a file you're modifying has grown unwieldy, including a split in the plan is reasonable.
  • 設計邊界清楚、介面定義良好的單元。每個檔案應該有單一清楚的職責。
  • 你對能同時放進上下文的程式碼思考得最好，而檔案越聚焦，你的編輯就越可靠。偏好較小、聚焦的檔案，勝過塞太多事的巨型檔案。
  • 一起變更的檔案應該住在一起。依職責拆分，而不是依技術層拆分。
  • 在既有程式碼庫中，遵循既有模式。如果程式碼庫使用大型檔案，不要單方面重構 —— 但如果你正在修改的檔案已經長到難以掌控，把拆分寫進計畫是合理的。

This structure informs the task decomposition. Each task should produce self-contained changes that make sense independently.

這個結構支撐任務的分解。每個任務應該產出自足的變更，且可以獨立理解。

Task Right-Sizing

任務尺寸調校

A task is the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate. When drawing task boundaries: fold setup, configuration, scaffolding, and documentation steps into the task whose deliverable needs them; split only where a reviewer could meaningfully reject one task while approving its neighbor. Each task ends with an independently testable deliverable.

一個任務是承載自己的測試循環、並值得一個全新審查者關卡的最小單位。在劃分任務邊界時：把設定、配置、脚手架與文件步驟併入需要這些產物的任務；只有在審查者可以有意義地否決一個任務、同時核准其鄰居任務的地方才拆分。每個任務都以一個可獨立測試的產物結束。

Bite-Sized Task Granularity

小塊任務粒度

Each step is one action (2-5 minutes): - "Write the failing test" - step - "Run it to make sure it fails" - step - "Implement the minimal code to make the test pass" - step - "Run the tests and make sure they pass" - step - "Commit" - step

每個步驟是單一動作（2-5 分鐘）： - 「撰寫失敗的測試」- 步驟 - 「執行它以確認它失敗」- 步驟 - 「撰寫能讓測試通過的最小程式碼」- 步驟 - 「執行測試並確認它們通過」- 步驟 - 「Commit」- 步驟

No Placeholders

Every step must contain the actual content an engineer needs. These are plan failures — never write them: - "TBD", "TODO", "implement later", "fill in details" - "Add appropriate error handling" / "add validation" / "handle edge cases" - "Write tests for the above" (without actual test code) - "Similar to Task N" (repeat the code — the engineer may be reading tasks out of order) - Steps that describe what to do without showing how (code blocks required for code steps) - References to types, functions, or methods not defined in any task

Self-Review

After writing the complete plan, look at the spec with fresh eyes and check the plan against it. This is a checklist you run yourself — not a subagent dispatch.

1. Spec coverage: Skim each section/requirement in the spec. Can you point to a task that implements it? List any gaps.

2. Placeholder scan: Search your plan for red flags — any of the patterns from the "No Placeholders" section above. Fix them.

3. Type consistency: Do the types, method signatures, and property names you used in later tasks match what you defined in earlier tasks? A function called clearLayers() in Task 3 but clearFullLayers() in Task 7 is a bug.

If you find issues, fix them inline. No need to re-review — just fix and move on. If you find a spec requirement with no task, add the task.

禁止占位符

每個步驟都必須包含工程師需要的實際內容。這些都是計畫失敗——絕不允許： - 「TBD」「TODO」「之後再實作」「補上細節」 - 「加入適當的錯誤處理」/「加入驗證」/「處理邊界情況」 - 「為上述撰寫測試」（沒有實際測試程式碼） - 「類似任務 N」（重複程式碼 —— 工程師可能不依順序閱讀任務） - 只描述要做什麼、卻不展示怎麼做的步驟（程式碼步驟需要程式碼區塊） - 引用任何任務中都未定義的型別、函式或方法

自我審查

寫完完整計畫後，以全新眼光看待規格，並據此檢查計畫。這是你自己執行的檢查清單 —— 不是子代理派發。

1. 規格涵蓋： 略讀規格中的每個段落/需求。你能指出實作它的任務嗎？列出任何缺口。

2. 占位符掃描： 搜尋計畫中的紅旗 —— 上方「禁止占位符」一節的任何模式。修正它們。

3. 型別一致性： 你在後續任務中使用的型別、方法簽名與屬性名稱，是否與較早任務中定義的一致？任務 3 中叫 clearLayers()、任務 7 卻叫 clearFullLayers() 的函式就是一個 bug。

如果發現問題，就地修正。不需要重新審查 —— 修好就繼續。如果發現某個規格需求沒有對應任務，就把任務加上去。

教學解說

撰寫計畫的核心原則是：假設執行者對你的程式碼庫零上下文。你寫的計畫不是給自己看的——是給一個完全不了解專案的人（或子代理）看的。

每個任務都應該小到 2-5 分鐘內完成，並且包含：要改哪些檔案、要寫什麼測試、如何驗證。任務太大會讓執行者迷失方向；太小會瑣碎到沒意義。

Worked Example（具體案例）

案例：為「使用者偏好設定」功能撰寫計畫

## Task 1: 建立資料模型
- 檔案：src/models/user-prefs.ts（新建）
- 內容：定義 UserPrefs interface（theme, language, notifications）
- 測試：src/models/__tests__/user-prefs.test.ts
- 驗證：tsc --noEmit 通過

## Task 2: 建立 API 端點
- 檔案：src/api/user-prefs.ts（新建）
- 內容：GET/PUT /api/user/prefs
- 測試：src/api/__tests__/user-prefs.test.ts
- 驗證：跑測試，確認 CRUD 正常

常見錯誤

錯誤後果正確做法
任務太大（「實作整個功能」）執行者迷失方向拆成 2-5 分鐘的小任務
不指定檔案路徑執行者亂猜放哪裡明確列出要改的每個檔案
不寫測試要求執行者可能跳過測試每個任務都附上測試要求

練習／檢核清單

  • □ 已確認範圍（如果太大，已拆成子計畫）
  • □ 已規劃檔案結構（哪些建立、哪些修改）
  • □ 每個任務都小到 2-5 分鐘可完成
  • □ 每個任務都指定了要改的檔案
  • □ 每個任務都附上測試要求
  • □ 每個任務都有驗證方式
  • □ 計畫已儲存到 docs/superpowers/plans/

進階真實情境 Worked Example

案例：為「訂單匯出 CSV」撰寫計畫——跨三個檔案、需要介面契約

  1. 讀規格——spec 說「匯出目前篩選結果、含標頭、UTF-8 BOM、欄位順序固定」
  2. 檔案結構——src/export/csv.ts（新建：CSV 序列化）、src/export/orders.ts（新建：查詢＋組裝）、src/api/routes.ts（修改：掛端點）、測試各一
  3. 任務切分——Task 1：CSV 序列化（純函式，可單獨測）；Task 2：訂單查詢與組裝；Task 3：路由掛接
  4. 關鍵：Interfaces 區塊——Task 1 的 Produces 寫明 serializeCsv(rows: Row[], opts): string 的完整簽名，Task 2 的 Consumes 引用它——因為執行每個任務的子代理只看自己的任務，介面契約是它們之間唯一的溝通橋
  5. Global Constraints——從 spec 逐字複製：「欄位順序：id, created_at, amount, currency」「UTF-8 含 BOM」「不匯出已刪除訂單」
  6. 每個步驟 2-5 分鐘——Task 1 含「寫失敗測試 → 跑失敗 → 最小實作 → 跑通過 → commit」五步，每步配實際程式碼
  7. 自我審查——逐段掃描規格，確認每條需求都有任務；搜尋「TBD／加錯誤處理／類似 Task N」這類占位符；檢查 Task 2 的型別名與 Task 1 的 Produces 一致

為什麼選這條路徑：計畫不是寫給自己看的筆記，而是寫給「零上下文、品味存疑」的執行者的契約。Interfaces 區塊的存在，是為了讓「只看 Task 3 的子代理」也能寫出與 Task 1 相容的程式碼——型別不一致是計畫最貴的 bug，因為它在執行中期才會爆炸。

深入原理擴充

writing-plans 的設計假設是「執行者不是寫計畫的 session」——無論是 subagent-driven-development 的全新子代理，還是 executing-plans 的另開 session，他們都沒有寫計畫者的上下文。因此計畫必須是自足的溝通載體：所有需求、值、簽名、驗證方式都要在計畫內完成閉環，不能依賴「執行者應該知道」。這解釋了「No Placeholders」的嚴格程度——「加適當的錯誤處理」對有上下文的人是真話，對零上下文的執行者就是一道無法兌現的指示。

「步驟小到 2-5 分鐘」是刻意對齊 agent 的錯誤半徑：任務越短，執行者偏離預期的機會越小，驗證點越密，錯誤被捕捉得越早。把「驗證」寫成每個任務的固定步驟（跑失敗 → 看失敗 → 實作 → 看通過），是讓「證據導向」滲透進計畫本身的文法。

陷阱案例：「類似 Task N」的偷懶寫法。計畫作者為了省字數寫「同上，改成列表版」，假設執行者會依序讀任務。但技能明說「工程師可能不依順序閱讀任務」——Task 7 的子代理只看 Task 7。省略的上下文不是「省字」，是「製造執行錯誤」。正確做法是重複必要程式碼：計畫的冗長是它的可靠性的代價。

進階挑戰題

  1. 「Interfaces」區塊的存在是為了讓任務可被獨立執行。如果省略它，任務之間的溝通靠什麼？這會在哪個時機點爆炸？
  2. 「把設定、配置、脚手架步驟併入需要它們的任務」與「只在審查者可獨立否決處拆分」——用這兩個準則判斷：一個「安裝相依＋建資料夾」的任務該不該獨立存在？
  3. 你的計畫有 Task 3 定義 clearLayers()、Task 7 卻寫 clearFullLayers()。這是哪一類計畫失敗？為什麼自我審查能抓到你而執行者抓不到？
